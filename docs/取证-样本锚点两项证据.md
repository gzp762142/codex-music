## 一、锚点是什么：**两个**，且都是硬编码立即数，**没有出处**

### 1.1 实测：样本里有**两个**锚点，相差恰好一页

| 锚点 | 构造指令 | 立即数拼装 |
|---|---|---|
| `0xFFFFFFE3831F8000` | `0x100F9C2B0` | `mov x1,#-0x8000` + `movk #0x831f,lsl#16` + `movk #0xffe3,lsl#32` |
| `0xFFFFFFE3831F4000` | `0x100F9C1D8` | `mov x1,#-0x3ff0` + `movk #0x831f,lsl#16` + `movk #0xffe3,lsl#32` |

两者**只差 `0x4000`（一页）**，而且分别喂给**两个不同的下游函数**：

```asm
; ── 锚点 A：0xFFFFFFE3831F8000 ──
100F9C2B0  mov  x1, #-0x8000
100F9C2B4  movk x1, #0x831f, lsl #16
100F9C2B8  movk x1, #0xffe3, lsl #32          ; x1 = 0xFFFFFFE3831F8000
100F9C2BC  bl   #0x100f9d08c                  ; -> kernel base 扫描（见 1.2）

; ── 锚点 B：0xFFFFFFE3831F4000 ──
100F9C1D8  mov  x1, #-0x3ff0
100F9C1DC  movk x1, #0x831f, lsl #16
100F9C1E0  movk x1, #0xffe3, lsl #32          ; x1 = 0xFFFFFFE3831F4000
100F9C1E4  bl   #0x100f96624                  ; -> 另一个下游
```

**这一条本身就削弱了"通用常量"的可能**：如果是设计常量，不会有两个、只差一页、
还喂给不同下游。

### 1.2 锚点 A 怎么用：读 `锚点 + 8`，不是 `+0x28`

`0x100F9D08C` 起始处（`x19` = 入参 `x1` = 锚点）：

```asm
100F9D0D0  mov  x8, #0x2102
100F9D0D4  movk x8, #0x914f, lsl #16
100F9D0D8  movk x8, #0x47e3, lsl #32
100F9D0DC  movk x8, #0xffd0, lsl #48          ; x8 = 0xFFD047E3914F2102
100F9D0E0  sub  x9, x19, x8                   ; 减常量
100F9D0E4  add  x9, x9, #8
100F9D0E8  add  x0, x9, x8                    ; 加回同一常量 -> 相互抵消
100F9D0EC  bl   #0x100f98dc0                  ; mc_kread64(x19 + 8)
```

**`sub` 与 `add` 用的是同一个常量 `0xFFD047E3914F2102`，算术上完全抵消 ——
这是混淆噪声**（与物理写侧那个 `0xF93A151819B5F3C5` 同一手法）。
实际语义就是 **`mc_kread64(锚点 + 8)`**。

> **更正**：此前分析报告写的是"锚点 + 0x28"。按本次逐字节核对，
> 这条路径读的是 **`锚点 + 8`**；函数内另有 `x22 + 0x30`（`0x100F9D13C`）的读取，
> 属于后续不同步骤。两处都应视为"锚点或其派生结构里的某个偏移"，
> **具体偏移量以本次反汇编为准**，不要沿用 `+0x28`。

### 1.3 结论：锚点**没有出处** —— 这回答了问题 ①

在整个二进制里，这两个锚点**只以 `movz`/`movk` 立即数形式存在**，
**不存在任何从其它数据计算它们的过程**：

- 不是 `kernelSymbol.X + 偏移` 算出来的；
- 不是从 config / plist / 环境变量读出来的；
- 字节级搜索 `0xFFFFFFE3831F8000` 的 8 字节序列命中 **0**（因为是指令立即数，不是数据常量）；
- 样本自己也**没有**对这两个值做任何版本判断或合法性校验 —— 直接拿去用。

**所以"锚点是什么对象"这个问题，在样本二进制里没有答案可查。** 它不是某个已知内核
符号的地址，也不是推导结果；它是**写死在代码里的、特定环境的一份记录值**。

### 1.4 而且它与本机地址空间形态对不上

- 锚点落在 `0xFFFFFFE3...` 段；
- 本工程目标设备（iPad14,3 / T8112 / iOS 16.4.1）的内核实测范围是 `0xfffffe...`
  （panic 日志：`KernelCache base 0xfffffe0019b08000`、`Zone map 0xfffffe100cae...`）；
- 两者**相差约 0x1E3 段级偏移**，不是同一段的相邻值。

**这条独立地支持"不能移植"**：即使锚点在样本那台设备上指向某个有效内核对象，
它在本机极可能落在未映射区 —— 而扫描一旦读它，就是整机重启。

## 二、扫描路线在本工程后端上是否可安全访问：**不可**（有实测代价）

### 2.1 后端的性质决定了"逐页读 4 字节"不安全

本工程的读原语（libkfd `kread_sem_open`）**不是"直接读那个地址"**：
它把一个本进程持有的内核对象的指针字段改写为 `目标地址 − delta`，
再由内核按内核语义从该指针起**逐字段读回**。因此：

- 内核实际访问范围**大于**请求的 4 字节；
- 只要目标页**未映射**，就是内核态 same-EL **data abort**；
- **没有 fault-recovery，也没有"读到垃圾"这个中间态** —— 只有重启。

`km_read_u32`（`KernelMemory.m:1105`）只约束**地址形态与页内边界**，
**证明不了那一页已映射**。所以"每页只读 4 字节所以安全"这个前提**不成立**。

### 2.2 这条路本工程已经走过，代价是两次彩屏

```
KernelMemory.m:670   反向扫描（唯一一处"在未验证地址上连续盲扫"的内核访问）已经整段删除，
                     g_kernel_base 不再有任何写入点
KernelMemory.m:2271  第二次彩屏的 far = 0xfffffe1564a385b4、DFSC=6 level 2 正是
                     "形态合法、页未映射"这个形态
KernelMemory.m:2276  它与"已经整段删除的那条 kernel base 反向盲扫"同一种赌
```

**样本那条路（锚点 + 向低地址逐页扫 `0xFEEDFACF`），就是本工程已经删掉的那一条。**

样本可以这么做，是因为它踩错最多返回失败；本工程踩错是**整机重启**。
这条差异不改，任何"逐页试"的做法都不能照搬。

### 2.3 出路不是"更好地验证锚点"，而是"先有映射验证能力"

`KernelMemory.m:2285-2287` 已写明恢复前提：拿到「**能证明某个地址确实已映射**」的手段
—— `ptov_table` 的等价物，或**逐级页表验证下钻**。

**本文的结论是：问题 ② 的答案与锚点无关。**
即使锚点明天被完全查清，只要"目标页是否已映射"仍不可判定，扫描就仍然是一次赌。
**顺序必须是：先有映射验证 → 再谈任何依赖"读未知地址"的路线。**

## 三、两项证据的最终状态

| 问题 | 结论 | 性质 |
|---|---|---|
| ① 锚点是什么对象 | **样本里查不到出处**：两个硬编码立即数、相差一页、喂给不同下游、无版本校验、无任何计算过程；且与本机地址段对不上 | **已定论（负面结论）** |
| ② 扫描地址是否可安全访问 | **不可**。后端无 fault-recovery；"只读 4 字节"不构成安全证明；本工程已因同类操作两次彩屏并删除该路径 | **已定论（负面结论）** |
| ③ 要做什么 | 不是"继续验证锚点"，而是**先实现 VA 映射验证原语**（见 `docs/交付任务-映射验证原语.md`） | 下一步 |

**换句话说：这两项"缺的证据"已经不必再找了 —— 它们的结果都是"此路不通"，
而这正好把方向收敛到唯一一条可走的路：先把"证明某地址已映射"做成能力。**
