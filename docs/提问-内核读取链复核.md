# 内核内存读取链：三处结论请复核

> 用法：整篇直接发给对方。三处问题各自独立，可以只答其中一处。
> 每处都请明确给出「成立 / 不成立 / 证据不足」，并附最小反例；不要用"通常""一般"这类措辞代替结论。

---

## 背景（最小必要）

平台：Darwin 22.4.0 / xnu 8796.102.5 / arm64e / 16K 页 / `T1SZ_BOOT = 17`。

读取原语（公开项目 libkfd 的 `kread_sem_open` 后端）：要读内核地址 `kaddr`，先把自己持有的一个内核对象的**指针字段**改写成 `kaddr - delta`，再调 `syscall(SYS_proc_info, PROC_INFO_CALL_PIDFDINFO, ...)`，由**内核**按内核语义从那个指针开始解引用，把结构体内容拷回用户态。

这条路径上内核没有注册 fault-recovery handler，所以内核一旦踩到未映射地址，结果不是本进程报错，而是**整机 panic**。因此每一次读之前只能做形态检查（地址是否落在内核 VA 域、是否对齐等），而这些检查都**不回答「这个地址已映射吗」**。

## 第一处：PAC 还原的算术与判据

库里的宏（`static_info.h:96-100`）：

```c
ONES(x)       = (1ULL << (x)) - 1
PTR_MASK      = ONES(64 - T1SZ_BOOT)      /* T1SZ_BOOT = 17 → 0x00007fffffffffff */
PAC_MASK      = ~PTR_MASK                 /* 0xffff800000000000 */
SIGN(p)       = ((p) & BIT(55))
UNSIGN_PTR(p) = SIGN(p) ? ((p) | PAC_MASK) : ((p) & ~PAC_MASK)
```

实测：内核里 `task` 结构的 `map` 字段（结构内偏移 `0x28`）读回来是 `0x52bc7e10023e93c0`。

**Q1.1** `UNSIGN_PTR(0x52bc7e10023e93c0)` 等于多少？请一步步算。

**Q1.2** 用**单个 bit（55）**判断"这个指针是否被签名"，这个判据可靠吗？请具体走一遍「一个确实被签名的指针，其 bit 55 == 0」的情形 —— 它会落到 `p & ~PAC_MASK` 分支，此时结果是什么？如果这个判据不可靠，正确的判据是什么？

**Q1.3** 对一个**本来就没被签名**的内核地址（bit 55 == 1），`UNSIGN_PTR` 是不是恒等变换？「内核 VA 的 bit 55 恒为 1」这个前提在 `T1SZ_BOOT = 17` 时成立吗？请给出理由，不要只说结论。

**Q1.4** 同一段代码里，上游对 `vm_map->pmap` 也做了同样的还原。哪些内核结构字段在 arm64e 上会被 PAC 签名、哪些不会？有没有一条可判定的规则（例如"凡是指向 zone 分配对象的 `__ptrauth` 字段"），而不是逐个实测？

## 第二处：一次整机 panic 的机制重构

panic 记录（16K 页）：

```
esr    = 0x96000007        EC = 0b100101 (same-EL data abort), DFSC = 0b000111 (level-3 translation fault)
far    = 0xfffffe1009577ffc
x8     = 0xfffffe1009577ff4        far == x8 + 8
Zone map: 0xfffffe10f10e4000 - 0xfffffe16f10e4000
kernel text base: 0xfffffe0022084000
Panicked task: pid 370
```

已知读取原语的下溢量（`kread_sem_open.h:147`）：

```c
u64 new_pinfo = kaddr - offsetof(struct pseminfo, psem_uid);
```

而 `struct pseminfo` 的定义（`static_info.h:556-567`）：

```c
struct pseminfo {
    u32  psem_flags;        /* 0x00 */
    u32  psem_usecount;     /* 0x04 */
    u16  psem_mode;         /* 0x08 */
    u32  psem_uid;          /* 0x0C  ← psem_mode 是 u16，psem_uid 对齐到 4 */
    u32  psem_gid;          /* 0x10 */
    char psem_name[32];     /* 0x14 */
    u64  psem_semobject;
    u64  psem_label;
    i32  psem_creator_pid;
    u64  psem_creator_uniqueid;
};
```

所以 `offsetof(struct pseminfo, psem_uid) = 0x0C`。

**我的重构：**

1. `x8` 是内核执行 `[x8 + 8]` 时的基址指针，也就是 `new_pinfo`。
2. 注意 `x8` 的低 4 位是 `4` —— **不是 8 字节对齐**。而送进这条原语的地址一定会被上游检查成 8 字节对齐，所以 `x8` 不可能是用户态送进去的地址，只能是内核自己算出来的 `new_pinfo`。
3. 于是 `kaddr = x8 + 0x0C = 0xfffffe1009578000`，是 **16K 页对齐**。
4. 内核实际访问的**最低地址**是 `kaddr - 0x0C`，落在**前一页**（`0xfffffe1009574000` 起那一页）的最后 12 字节；那一页未映射 → level-3 translation fault → 整机 panic。

**Q2.1** 这个重构成立吗？有没有隐含假设或漏洞？

**Q2.2** 请**具体列出所有别的机制**，它们同样能产生 `far == x8 + 8`、`DFSC = level-3`、以及 `x8` 指向 `0xfffffe1009577ff4` 这样的值。要具体到机制，不要泛泛而谈"也可能是别的原因"。

**Q2.3** 若重构成立，正确的闸门是什么？我目前的写法是：对 `[addr, addr+len)` 内**每一个 8 字节字的地址**，要求「页内偏移 `>= delta`」，其中 `delta = 0x0C`。这个写法够吗？还有没有别的下溢源 —— 例如内核把整个 `struct pseminfo` 拷回来，只要 `kaddr` 靠近页尾就可能**向上**跨到下一页？

**Q2.4** 写路径（`kwrite_dup.h:126`，`new_fp_guard = kaddr - offsetof(struct fileproc_guard, fpg_guard)`）自身下溢 `0x08`；但 `kwrite_dup.h:110` 在真正写入之前会先用**同一个 kaddr** 做一次 8 字节读，那一步仍按 `0x0C` 下溢。所以我把写路径的闸门取成 `max(0x0C, 0x08) = 0x0C`。这个推理对吗？还有没有第三个我漏掉的下溢源？

## 第三处：一条结构体关系恒等式

同一个库里**两个方向都在用**同一条等式（`proc__object_size = 0x730`，iOS 16.4+）：

正向（`info.h:137`）：

```c
kfd->info.kaddr.current_task = kfd->info.kaddr.current_proc + dynamic_info(proc__object_size);
```

反向（`kread_sem_open.h:100-101`）：

```c
u64 task_kaddr = static_kget(struct semaphore, owner, semaphore_kaddr);
u64 proc_kaddr = task_kaddr - dynamic_info(proc__object_size);
/* 然后沿 proc__p_list__le_prev 往回走，找 p_pid == 自己的那个 proc */
```

而这个库在 iOS 16.x 上被广泛使用、能用。

**Q3.1** 两个方向同时成立，说明 `struct proc` 与 `struct task` 在分配上相邻（`task` 紧跟在 `proc` 之后）。这个推断对吗？如果不是"相邻分配"而是别的机制，是什么？

**Q3.2** `proc + 0x730` 一定落在**该 proc 自己的** task 上吗？有没有可能落在相邻的另一个 proc、或 proc_zone 里的空闲槽上？判断依据是什么（zone 的 quantum / size class 对齐？`proc_zone` 与 `task_zone` 是否是同一个 zone？）

**Q3.3** 如果要在运行时**证伪**这条等式，有什么低风险的做法？（约束：不能对未确认地址解引用 —— 在这条路径上解引用一个未映射地址就是整机 panic，所以"读一下看看"不是可选项。）

**Q3.4** 有没有一条**不需要**这条等式就能拿到当前进程 `task` 指针的路？（例如从已有的 `kernel_proc` / `allproc` 链、或从 Mach port / thread 侧反查。）
