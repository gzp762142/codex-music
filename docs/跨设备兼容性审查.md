# 跨设备兼容性审查（除本机 iOS 16.4.1 之外的所有条目）

审查对象：`Aether/libmemrw/kfd/libkfd/info/dynamic_info.h`（版本表，7 条）
本机已验证：`[#3] Darwin 22.4.0`（iPad Pro M2 / T8112 / iOS 16.4.1）

**结论先说**：本机之外有 **5 条条目存在会让客户设备崩溃或功能失效的问题**，其中 2 条是「静默选错偏移表」——最危险的一类，因为不报错、直接崩。

---

## 一、致命：两条 `22.6.0` 条目前缀相同，后者永不可达

```
[#5] .kern_version = "Darwin Kernel Version 22.6.0: ... RELEASE_ARM64_T8101"   // iOS 16.6 iPhone 12 Pro
[#7] .kern_version = "Darwin Kernel Version 22.6.0: ... RELEASE_ARM64_T8112"   // iPhone 15,3 (14 Pro Max)
```

`info_init` 的匹配逻辑（`info.h:116`）：

```c
const u64 kfd_version_prefix_length = 29;   /* strlen("Darwin Kernel Version 22.5.0") */
if (!strncmp(kern_version, current_kern_version, kfd_version_prefix_length)) { vid = i; return; }
```

**前 29 字符恰好止于 `'22.6.0:'`，而两条 `kern_version` 的前 29 字符完全相同** → 循环在 `[#5]` 就命中并 `return`。

于是：

| 设备 | 实际选中 | 后果 |
|---|---|---|
| iPhone 12 Pro (T8101) 类 | `[#5]` | 偏移表内容对，但 `T1SZ_BOOT` 硬编码 17 → 错（见第四节） |
| **iPhone 14 Pro Max (T8112) 类** | **`[#5]`（错）** | **用 T8101 的偏移 + T1SZ=17 跑在 T8112 上** |

`[#7]` 是**死条目**。而 `[#7]` 的 `.kern_version` 里写了真实构建号 `xnu-8796.141.3~6`（与 `[#5]` 的 `8796.142.1` 不同），说明它是**另一个内核构建**——偏移大概率不通用。

**这是最隐蔽的问题：不报错、不 assert，直接选错表。**

---

## 二、致命：iOS 15.x 条目的 IOSurface 偏移全为 0

```
[#1] .kern_version = "Darwin Kernel Version 21.0.0"   // iOS 15.x
     .ios__IndexedTimestampPtr = 0,
     .ios__AllocSize           = 0,
     .ios__PixelFormat         = 0,
     .ios__UseCountPtr         = 0,
     .ios__ReadDisplacement    = 0,
```

而 iOS 15 的设备在 `KernelMemory.m` 里会被分派到 **IOSurface 后端**：

```c
if (@available(iOS 16.0, *)) { readMethod = kread_sem_open; }
else                        { readMethod = kread_IOSurface; }   // ← iOS 15 走这里
```

`kread_sem_open` 不依赖 `ios__*` 字段，但 **`kread_IOSurface` 完全依赖它们**（拿它们当读地址与 search 判据）。全为 0 意味着：

- 写路径会把「目标地址」算成 `0 + 0`
- search 判据 `PixelFormat == 0`(IOSURFACE_MAGIC) 永远不成立，或匹配到错误对象

**iOS 15 设备必崩，且是内核层面的操作失误。**

> 注：表头注释说这些字段"deliberately nil"，但那只对 `kernelcache__*` 成立（有注释说明），`ios__*` 没有同样的说明——它们被别的条目填了真值，所以留 0 是缺漏而非设计。

---

## 三、高危：`perf_supported = true` 的条目用的是「特定机型」偏移

```
[#4] Darwin 22.5.0   perf=true   kernelcache__* = 8 项真值   // 注释：iOS 16.5 - iPhone 14 Pro Max
[#5] Darwin 22.6.0   perf=true   kernelcache__* = 8 项真值   // 注释：iOS 16.6 - iPhone 12 Pro
[#7] Darwin 22.6.0   perf=false  kernelcache__* 全 0
```

`kernelcache__*` 是**内核静态符号地址**（`vn_kqfilter`、`ptov_table`、`gVirtBase`…），它们随**内核构建**变化，而不同 SoC/机型在同一个 iOS 版本上**未必是同一份 kernelcache**。

`perf_run()` 拿它们去算 kernel slide 与 kernel base，然后：

```c
// perf.h:114
mh_header[0] = kread_sem_open_kread_u32(kfd, kernel_base);
assert(mh_header[0] == 0xfeedfacf);   // ← 偏移不对就在这里失败
```

**若 `kernel_base` 算错 → `kread` 打在错误/未映射内核地址上 → 与 22.4.0 那次同型的失败。**

而 `#4` 与 `#5` 的注释各自只声明了一个机型（14 Pro Max / 12 Pro），却会因为前缀匹配覆盖**该 Darwin 版本下所有设备**——即：

- 任何跑 iOS 16.5 的非 14 Pro Max 设备，都会用 14 Pro Max 的 kernelcache 偏移
- 任何跑 iOS 16.6 的非 12 Pro 设备，都会用 12 Pro 的偏移

**这是给客户用时的最大隐患面。**

---

## 四、高危：`T1SZ_BOOT` 是编译期硬编码

```c
// static_info.h:22
#define T1SZ_BOOT    17ull
// static_info.h:97-100
#define PTR_MASK         ONES(64-T1SZ_BOOT)          // = ONES(47)
#define PAC_MASK         (~PTR_MASK)                 // = 0xFFFF800000000000
#define UNSIGN_PTR(p)    (SIGN(p) ? ((p) | PAC_MASK) : ((p) & ~PAC_MASK))
```

按提交历史自己的记录（`kfd-docs.md`）：

> change `t1sz_boot` to `17ull` **if iPhone 14** or `25ull` **if not iPhone 14**

所以：`17` 只对 **iPhone 14 系列 / A16 / M 系**成立；**A15 及更早需要 25**。

影响面：`UNSIGN_PTR` 被用在真正关键的地方——

```
info.h:145/152/167/174   current_map / current_pmap / kernel_map / kernel_pmap
perf.h:98/104/105/106/123/124/125/135   fileproc / fp_glob / fg_ops / cnode / cdevsw
kwrite_dup.h:43          (fp->fp_glob > PTR_MASK) 判据
```

`T1SZ_BOOT` 错 → `PTR_MASK` 错 → **内核 VA 的高位被错误清除** → `kernel_map` / `kernel_pmap` 变成垃圾 → 后续全错。**且没有任何编译期或运行期检查会拦住它。**

自检 `current_proc->p_pid` 也拦不住（那一步不走 `UNSIGN_PTR`）。

## 五、中危：表里混着 macOS 条目，且 `kern_version` 是占位串

```
[#6] .kern_version = "todo"        // macOS 13.4 - MacBook Air M2
[#7] 之后还有 macOS 13.5 / 13.6 …
```

- 这些条目在本工程（iOS）下**永远不会命中**，是噪音
- 已把 `info.h` 的比较从 `memcmp` 改成 `strncmp`，消除了「`memcmp` 读满 29 字节而字面量只有 5 字节」的越界读
- 但**建议直接删掉**：一个 iOS-only 的 kfd 里留着 macOS 占位条目，只会在下次有人改表时被误用

## 六、逐条目体检表

| 条目 | Darwin | 声明机型 | 偏移完整 | PUAFF 适用 | 问题 |
|---|---|---|---|---|---|
| `[#1]` | 21.0.0 | iOS 15.x | ✗ `ios__*` 全 0 | physpuppet | **IOSurface 后端必崩** |
| `[#2]` | 22.0.0 | iOS 16.0–16.4.1 | ✓ | physpuppet→landa | 注释与实际分派不符（见下） |
| `[#3]` | 22.4.0 | iOS 16.4.1 | ✓（本机验证） | landa | 已修 `perf_supported` |
| `[#4]` | 22.5.0 | iOS 16.5（14 Pro Max） | ✓ | landa | kernelcache 偏移仅对 14PM 保证 |
| `[#5]` | 22.6.0 | iOS 16.6（iPhone 12 Pro） | ✓ | landa | **抢占所有 22.6.0，含 T8112** |
| `[#6]` | macOS | — | ✗ 占位 | — | 死条目 + `"todo"` |
| `[#7]` | 22.6.0 | iOS 16.6（T8112） | ✗ 全 0 | landa | **永不可达（被 `[#5]` 抢）** |

### 另一个一致性问题：注释 vs 实际分派

`[#2]` 注释写 "iOS 16.0 - 16.4.1"，但 PUAFF 分派是：

```c
if (@available(iOS 16.4, *)) { puafMethod = puaf_landa; }
else                         { puafMethod = puaf_physpuppet; }
```

即 **16.0–16.3 走 physpuppet，16.4+ 走 landa**。而 `physpuppet` 在 iOS 16.4 已被修复（CVE-2023-23536），所以 16.0–16.3 的设备**只能用 physpuppet**——这条是对的，但注释没有体现，容易误读。

---

## 七、修复建议（按客户影响面排序）

### 建议 1：把 `perf_supported` 全部置回 `false`（最高收益）

理由：`#4`/`#5` 的 kernelcache 偏移**只对其声明的那一个机型保证**，而现在它们会因为前缀匹配覆盖该 Darwin 下所有设备。给客户用时，这个不确定性远大于 perf 带来的收益（perf 只是把 kread 从"半随机游走"升级成更高效的物理读写，不是功能必需）。

```c
// 全表统一：kernelcache__* 留 0，perf_supported = false，靠扫描找 kernel base
```

这样 `perf_run` 直接返回，消除「kernel cache 偏移不匹配 → kread 打错地址」这一整类风险，**和我们刚给 22.4.0 做的处理一致**。

### 建议 2：修 `22.6.0` 的条目抢占

最干净的做法是**删掉 `[#5]`（T8101/iPhone 12 Pro）**，只保留 `[#7]`（T8112）。但 `[#7]` 现在 `kernelcache__*` 全 0、`perf_supported=false`——配合建议 1 正好自洽。

若必须同时支持两类设备，则需要把匹配键延长到能区分 SoC 后缀（即前缀 > 29 字节，让 `RELEASE_ARM64_T8112` 参与比较），**并同时解决 `T1SZ_BOOT` 的按设备取值问题**（建议 3）。

### 建议 3：`T1SZ_BOOT` 改成运行期决定

它现在是 `#define`，无法在运行时按设备分支。改法：把 `PTR_MASK` / `PAC_MASK` / `UNSIGN_PTR` 从编译期宏改成读一个运行期全局：

```c
static u64 g_t1sz_boot = 17;            /* 默认 iPhone 14 系 */
#define PTR_MASK  (ONES(64 - g_t1sz_boot))
```

或在 `km_init` 里用 `hw.cpufamily` / 机型判断后设置，再让 kfd 用它。

> 注意：这属于结构性改动（宏变变量，会影响所有使用点），**不要和本次止血混在一起做**。

### 建议 4：补齐或明确禁用 iOS 15

`[#1]` 的 `ios__*` 全 0。二选一：
- 从真实 iOS 15 设备上取到 IOSurface 偏移并补齐
- 或在 `km_init` 里**显式拒绝 iOS 15**（比现在"接受然后崩"好）

### 建议 5：删掉 macOS 条目

`[#6]` 及之后的所有 macOS 条目，从这个 iOS-only 工程里移除。

---

## 八、给客户前必须明确的事

**上面每一条我都只做了静态核对，没有真机验证。** 尤其建议 1（关掉 perf）会改变 `#4`/`#5` 设备的行为——虽然我的判断是"更安全"，但那需要在一台真实 16.5 或 16.6 设备上确认。

在只有你这台 16.4.1 可测的情况下，能确定的是：

- ✅ `[#3]`（本机）修完后逻辑自洽
- ⚠️ `[#4]`/`[#5]`（16.5/16.6）**当前会在非声明机型上选错偏移表**——这是确定的代码事实，不是推测
- ⚠️ `[#7]` 是死条目——确定的代码事实
- ⚠️ `[#1]`（iOS 15）会崩——确定的代码事实

**建议先把建议 1 + 2 做掉再发客户**，这两条能消除"选错偏移表"这类静默致命问题。
