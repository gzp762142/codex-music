## 已定案：physrw 走样本那条路，PPL 不是障碍（2026-09-22）

### 0. 最要紧的一条：**PPL 不拦「kwrite 写页表页」**（Dopamine 源码级证据）

来源：`opa334/Dopamine` 2.x，本地克隆在 `D:\工作区\_Aether_rev\refs\Dopamine\`。

`BaseBin/libjailbreak/src/primitives.c:140-149`：

```c
int physwritebuf(uint64_t physaddr, const void* input, size_t size)
{
    if (gPrimitives.physwritebuf) {
        return gPrimitives.physwritebuf(physaddr, input, size);
    }
    else if (gPrimitives.kwritebuf && gPrimitives.phystokv) {
        return _physwritebuf_virt(physaddr, input, size);   // ← kwrite + phystokv
    }
    return -1;
}
```

而 `physrw_pte_handoff()`（`physrw_pte.c:104-149`）在**还没有 physrw 能力**的阶段就调用了
`physwrite64`（`:132`、`:140`）—— 所以它必然走上面第二条：
**物理地址经 `phystokv` 转成内核 VA，再用 `kwrite` 写进去。**

**结论：在 iOS 15/16 上，用内核写原语直接写页表页是可行的，PPL 不拦。**

**这纠正了两处此前的错误判断**：
1. ~~"iOS 16 的 PPL 会拦掉非 PPL 代码对页表页的写"~~ —— 错，Dopamine 就是反例；
2. ~~"样本用用户态 `str` 写 PTE 所以 PPL 管不着"~~ —— 该前提从未被独立验证（子代理明确指出），
   且**真因与它无关**：PPL 本来就不拦这条路径。

### 0.1 Dopamine 有两条 physrw 路，首选那条要 kcall

`launchdhook/src/boomerang.c:86`：

```c
bool physrwPTE = firstRetrieval && !is_kcall_available();
```

- **首选（有 kcall 时）**：`kernel.c:196` 用 `kcall` 调内核自己的
  `pmap_enter_options_addr(pmap, va, pa, VM_PROT_READ|VM_PROT_WRITE, ...)`
  ——**让内核去建映射，自己根本不碰页表**，所以与 PPL 无关。
- **备选（无 kcall 时）**：`physrw_pte` —— 手工造一块页表窗口，逐条写 PTE，
  走的是上面那条 `kwrite + phystokv`。
- 备选路还挑设备：`device_supports_physrw_pte()` 在 A8（typhoon）上返回 false
  （"causes SUPER WEIRD UNEXPLAINABLE SYSTEM RESTARTS"），Aether 的目标机不在排除之列。

**Aether 没有 kcall**（那需要 gadget 链，样本里有 `kernelGadget.*` 而 Aether 没有）。
**但 Aether 不需要它** —— 备选路只要 `kwrite` + `phystokv`，而这两样都在手上
（`kwrite` = `kwrite_sem_open`；`phystokv` 用兜底式 `pa - gPhysBase + gVirtBase`）。

### 0.2 两组 PTE 常量是同一套（交叉印证）

```c
// Dopamine  BaseBin/libjailbreak/src/pte.h:13
#define KRW_URW_PERM   (0x60000000000040)     // 内核读写 + 用户读写
```

样本写进 PTE 的 `0x0060000000000e43` 拆开正是 **同一个 `0x60000000000040`**
加低位 `VALID|TYPE|SH|AF|nG`。**样本与 Dopamine 用的是同一套 PTE 编码。**

> 样本三处构造点（`orr <pte>, <pa>, #0x6000000000000e43`）：
> `0x101049060` / `0x10104ce24` / `0x1010524e8`。
> **注意 `0x0060000000000e43` 的 bits[47:12] 全 0（PA=0），它是模板不是成品**
> —— 必须先 `pa | 它`。裸写等于把 VA 指到物理页 0，立刻彩屏。

### 0.3 仍然未决的一条（子代理标为最关键）

样本那三处 `str` 的**存储地址 provenance**：是 PUAF 窗口的用户 VA，还是 kwrite 的目标 KVA？
子代理未做通（样本 250 MB，`0x3d0/0x3d8` 同型偏移全文数百处，静态无法唯一定位）。

**但这条已经不再阻塞**：既然 PPL 不拦 `kwrite` 写页表（§0），两条 provenance 都可用 ——
若是 KVA，就直接走 `kwrite + phystokv`；若是用户态窗口 VA，就说明 PUAF 窗口里有页表页。
**先按前者推进，成本最低。**

### 0.1 样本不用 kcall（确证）——所以「补 kcall」这件大活可以直接砍掉

**判定**：样本的 8 个 `kernelGadget.*`（`br_x22` / `kcall_return` / `pacda` /
`exception_return_after_check(_no_restore)` / `ldp_x0_x1_x8` / `str_x8_x9` / `str_x0_x19_ldr_x20`）、
`ml_sign_thread_state`、`pmap_enter_options_addr`（两个同名键）、`pmap_remove_options`
—— **共 12 个键，在 38 个 `bl xpf_item_resolve` 调用点里一个都没出现**。

唯一沾边的是 `kernelSymbol.pmap_enter_pv`（`0x101cd2d00`，调用点 `0x101040d40`），
但它的用法是**能力探测**而非调用：

```
0x101040d40  bl  xpf_item_resolve
0x101040d44  cmp x0, #0        ← 只做空判断
0x101040d48  cset w8, eq
0x101040d58  br  x8            ← CFF 状态分发，不是 kcall
```

**三条独立封口**：
1. 页级穷举（853 个 `adrp`，window 12）→ 每个键只有 2 个 materialization 点
   （注册处 `adrp+add x0` + 字符串解密 `strb`），**没有第三类引用点**；
2. 全文件 345 MB 的 8 字节扫描（13 个键地址 + resolve/register 函数地址）→ **零命中**，
   排除「把键指针藏数据段再加载」与「间接调用 resolve」两条后路；
3. physrw 三处 PTE 写入点（`0x101049060` / `0x10104ce24` / `0x1010524e8`）所属函数的
   571 个 `adrp+add` 中，命中这些键的次数 = **0**。

**结论**：样本 = Dopamine 的 **`physrw_pte` 那条路**（写 PTE），不是首选路（kcall 调
`pmap_enter_options_addr`）。那些 gadget 键与 `ppl_*` 一样，是随 XPF 整库进来、登记完闲置的。

**对 Aether**：不需要实现 kcall（那要 gadget 链 + PAC 处理，是大工程）。
需要的仍然只有 **`kwrite` + `phystokv`**，两样都在手上。

> **方法论修正（必须传下去）**：`xpf_item_resolve` 内部会 `blr x8` 惰性调用节点的注册
> resolver（`0x10102f294 ldp x8,x0,[x20,#0x10]` → `0x10102f298 blr x8`，节点布局
> `next@0 / key@8 / fn@0x10 / arg@0x18 / inited@0x20 / result@0x28`，链表头 `*0x101d227b8`）。
> **所以"resolver 在 bl 图里 0 个调用者"不能单独当作"闲置"的证据** —— 对活键同样成立。
> 正确判据是「**这个键有没有进入 `xpf_item_resolve`**」。
> （`ppl_*` 那次结论侥幸没错，是因为它同时满足"从未被 resolve"。）

### 0.4 页表页来源：**(I) 确证 —— 样本就是 Dopamine 的 `physrw_pte` 那条路**

**一句话**：样本先在内核侧**建出**一张页表页，再用**一次物理写**把该页表页的**第 0 项写成指向它自己**
（自映射）。建好自映射之后，那个固定地址才变成普通 `str` 可写的页表页。

**决定性现场**（函数 `[0x101049a7c, 0x10104cf00)` 内，VA `0x10104cdc0` 起）：

```
0x10104cdc8  bl   #0x101093820        ; ret1 = L1_BLOCK_SIZE
0x10104cdd0  bl   #0x1010939d0        ; ret2 = L1_BLOCK_COUNT
0x10104cdd4  sub  x8, x0, #1
0x10104cdd8  mul  x1, x8, x26         ; x1 = (COUNT-1)*SIZE = 0x7000000000
0x10104cddc  mov  x0, x25             ; x0 = pmap
0x10104cde8  bl   #0x1010488e0        ; ★ 在 0x7000000000 上取/建页表 → 返回页表页地址
0x10104cdec  mov  x25, x0             ; x25 = magicPT
0x10104ce24  mov  x21, #0xe43
0x10104ce28  movk x21, #0x60,lsl#48   ; x21 = 0x0060000000000e43（L3 叶项模板）
0x10104ce2c  orr  x1, x25, x21
0x10104ce30  mov  x0, x25
0x10104ce34  bl   #0x10104f800        ; ★ physwrite64(magicPT, magicPT|PTE) = 自映射
```

- `0x10104f800` = `physwrite64(pa,val)`：`str x1,[sp,#8]; add x1,sp,#8; mov w2,#8; bl 0x10104e8c0`；
  后端 `0x10104e8c0` 走 `ldr x8,[0x101d228a0]; blr x8`。
- `0x10104ce08-ce34` 之间**没有任何** `mach_vm_allocate` / `vm_allocate` / `vm_map` / `mmap`
  —— **唯一的"做实"动作就是这次物理写**。

**与 Dopamine 逐字同构**（这就是我此前要的那个判定）：

```c
// Dopamine BaseBin/libjailbreak/src/physrw_pte.c
:13   #define MAGIC_PT_ADDRESS (L1_BLOCK_SIZE * (L1_BLOCK_COUNT - 1))
:125  int exp_r = pmap_expand_range(pmap, MAGIC_PT_ADDRESS, L2_BLOCK_SIZE);
:132  physwrite64(magicPT, magicPT | PERM_TO_PTE(PERM_KRW_URW) | PTE_NON_GLOBAL
                                | PTE_OUTER_SHAREABLE | PTE_LEVEL3_ENTRY);
:48   for (int i = 2; i < L2_BLOCK_COUNT; i++)    ← acquire_window 从 i=2 开始
```

样本侧一一对应：地址同公式（`(COUNT-1)×SIZE`）、在建出的页表上写自映射、
写入常量同值（`| 0x60…` 是样本额外加的 `NX|PXN`）、窗口槽从 **`w22` 初值 = 2** 开始。
**参数名不同（Dopamine 用 511，样本用 7），是因为 Dopamine 取"最后一个 L1 块"、
样本取第 7 块 —— 公式同一个，取值不同。**

**(II) 已排除**：`0x7000000000 = L1_BLOCK_COUNT × L1_BLOCK_SIZE` 是**用户地址空间上界**
（iOS 16K 的 `MACH_VM_MAX_ADDRESS`），`vm_map`/`vm_allocate` 在该地址必返
`KERN_INVALID_ADDRESS`；PUAF 窗口（内核随机选址）不可能落在它上面；
且样本自己把这个地址当"要建的地址"传给建表函数。

**地址推导（独立复核过）**：`0x101093820` 出口读 `[0x101cfff78]`(`_vm_kernel_page_size`)
→ 16K 返 `0x1000000000`（=L1 块）、4K 返 `0x40000000`；`0x1010939d0` 同源
→ 16K 返 `8`、4K 返 `0x100`（=L1 块数）。于是 16K：`(8−1)×2^36 = 0x7000000000` ✓、
4K：`0xFF×2^30 = 0x3FC0000000` ✓ —— 与 `0x100ff3548/3564/3580` 三个立即数逐位一致。

**这条同时回答了两个悬了很久的问题**：

1. **样本走的是 Dopamine 备选路（`physrw_pte`），不是自研新路线** —— 是同一算法的移植/变体；
2. **它不需要 kcall** —— 建页表这一步走的是**物理读+物理写**，不是 kcall 去调
   `pmap_expand_range`（与 §0.1「kcall 键从未被 resolve」完全自洽）。

**仍未确证（严格与证否分开）**：
1. `0x1010488e0` 内部让内核**分配新表**的具体机制（kcall vs 纯读写手工串表）——
   只确证它做 `base+idx*8 → physread64(0x10104f878) → &0xfffffffff000` 的页表遍历并返回表地址；
2. 物理写后端那个全局指针槽 `[0x101d228a0]` 的**写入者**未定位
   → "任意物理读写的最终来源"未确证；
3. `magicPT+8`（`sw_asid` 项，Dopamine `:140`）的写入未定位。

### 0.5 建表那一步怎么做：**备选路本来就不需要 kcall**（源码级，2026-09-22 修正）

**此前一句「备选路要 kcall」是错的，此处修正。**

Dopamine `BaseBin/libjailbreak/src/util.c:252` 的 `pmap_expand_range` **有两个分支**，
而且**无 kcall 那一支是完整的**：

```c
int pmap_expand_range(uint64_t pmap, uint64_t vaStart, uint64_t size)
{
    uint64_t ttep = kread_ptr(pmap + koffsetof(pmap, ttep));
    if (is_kcall_available()) {
        /* 让内核用 pmap_enter_options 建表；再把映射 pmap_remove 掉，
           但先把 pmap->type 设成 3(nested) 以保住那张空表，之后再改回 0。
           —— 这条反而更绕，因为"建好又要撤"。 */
    } else {
        /* 用户态手工串页表，全程只有页表遍历 + 物理写： */
        for (每个 L2 块) {
            do {
                uint64_t pte = 0;
                vtophys_lvl(ttep, va, &leafLevel, &pte);        // ① 页表遍历
                if (leafLevel != PMAP_TT_L3_LEVEL) {            // ② 这一级还没有下级表
                    leafLevel++;
                    uint64_t newTable = pmap_alloc_page_table(pmap, pt_va);
                    physwrite64(pte, newTable | ARM_TTE_VALID | ARM_TTE_TYPE_TABLE);  // ③ 物理写
                }
            } while (leafLevel < PMAP_TT_L3_LEVEL);
        }
    }
}
```

`pmap_alloc_page_table`（`util.c:224-250`）同样是纯物理写：

```c
uint64_t tt_p  = alloc_page_table_unassigned();   // 要一张"未关联"的页表页
uint64_t ptdp  = pvh_ptd(pai_to_pvh(pa_index(tt_p)));
physwrite64(ptdp_pa + koffsetof(pt_desc, pmap), pmap);      // 关联到目标 pmap
physwrite64(ptdp_pa + koffsetof(pt_desc, va) + …, va + po); // 关联到目标 VA
return tt_p;                                                // 返回新表的物理地址
```

**所以两条路的条件正好相反于我先前的表述**：

| | 要什么 | 机制 |
|---|---|---|
| **首选路**（`pmap_enter_options_addr`） | **要 kcall** | 让**内核**去建整块映射，必须能调内核函数 |
| **备选路**（`pmap_expand_range` 无 kcall 支） | **只要「页表遍历 + 内核写原语 + phystokv」** | 用户态**手工串页表**，每步自己读表、写表项 |

**因此样本「无 kcall 却走备选路」完全自洽** —— 正是 `launchdhook/src/boomerang.c:86`
那行 `bool physrwPTE = firstRetrieval && !is_kcall_available();` 的含义：
**没 kcall 就退备选路，而备选路不需要 kcall。**

**对 Aether 的直接结论**：照抄 `util.c:303-335` 那一支，需要的三样全在手上 ——

```
① 页表遍历      pmap->ttep 起逐级下行（第一段只读验证要确认的就是这个）
② 内核写原语    km_write（kwrite_sem_open，kopen 已在设备上跑通）
③ phystokv      兜底式 pa - gPhysBase + gVirtBase（三个基准值已读到且自洽）
```

### 1. 一手来源：kfd 作者对 PPL 的原话（原判断的出处）

**结论（一手来源）**：kfd 作者 Félix Poulin-Bélanger 的
[Exploiting PUAFs](https://raw.githubusercontent.com/felix-pb/kfd/main/writeups/exploiting-puafs.md)
原文：

> **PPL surprisingly does very little to prevent this technique.** Of course, it prevents the
> PUAF pages from being reused as page tables and other PPL-protected structures.

**这句话要拆成两半读，读错就全盘皆错**：

- **PPL 挡的是**：把 PUAF 页**重新分配成**页表页（kfd 作者本想在 Linux 上照搬 Jann Horn 那条路，
  在 iOS 上被 PPL 挡死，他因此只能改走 object-spray 拿 kread/kwrite，再靠 perf 兜底）。
- **PPL 不管的是**：那个页**本来就是页表页**、只是同时落进了 PUAF 窗口 —— 此时修改它
  用的是**用户态普通 `str`**，走的是用户映射那条路，根本不进 PPL 管辖的内核映射路径。

**样本走的正是后者**。指令级证据：`0x101048e78` 里
`mov x8,#0xe43` / `movk x8,#0x60,lsl#48` / `orr` / `str ...`，写进去的常量
`0x0060000000000e43` 位域解出来是：

```
bit54 NX=1, bit53 PXN=1       ← 不可执行
低12位 0xe43: VALID=1 TYPE=1 AP=1 SH=1 AF=1 nG=1
                ↑ AP=1 表示 **EL0（用户态）可读可写**
```

**一条普通用户态 `str`、一条明确授权用户态访问的 PTE —— 全程不经过内核映射，PPL 无从拦起。**

**推论**：Aether 不需要实现 PPL 绕过（与样本逆向的结论一致：样本那 12 个 `ppl_*` 键
零调用者、`blr` 数 0）。真正要解决的是**窗口里怎么出现页表页**这一环。

## physrw 五步与 Aether 现状

| 步骤 | 样本做法 | Aether 现状 |
|---|---|---|
| ① PUAF 拿到可写窗口 | landa | **已有**（`kopen` 在设备上成功过，走的 landa） |
| ② 窗口地址上出现**页表页** | 样本走 `0x1010488e0`（内部机制未确证，见 §0.3）；Dopamine 的无 kcall 路 = `pmap_expand_range` 逐级 `vtophys_lvl` + `pmap_alloc_page_table` + 写父级表项 | **只读探针已完成**（`KernelPhysWindow` + 面板「建窗」）；**建表本身正在移植** ← 当前重点 |
| ③ 自映射：把这张页表页挂进它自己 | 样本 `0x10104ce34` = `physwrite64(magicPT, magicPT \| PTE)` | 待实现（与 ② 同一次移植） |
| ④ 把目标物理页的 PTE 写进窗口 | 用户态 `str`，值 `pa \| 0x0060000000000e43` | 待实现；③ 一旦成立，这一步**不再需要 kread/kwrite**（这就是整条路的意义） |
| ⑤ 刷 TLB + 本地 `memcpy` 读 | 样本 `0x10104f800` 另写 `magicPT+8`（指向 `pmap->sw_asid` 那一页）供 `flush_tlb` | 待实现 |

**注意**：这条路**不需要 `ptov_table`** —— 前几轮卡在 `ptov_table` 的排查，修的是一条样本不走的岔路。
但 **PA → KVA 换算本身仍然需要**：页表项里装的是物理地址，下钻时得补成内核 VA 才能 kread/kwrite。
现在走 `km_phystokv()` 的兜底支 `pa - gPhysBase + gVirtBase`；`gVirtBase` / `gPhysBase` /
`gPhysSize` 三个量已读出且互相自洽（`gPhysSize` 与设备物理内存量吻合），但 `gVirtBase`
与某个外部期望值差 `0x3b7e198` —— 该差值**尚无定论**，所以算出来的每个地址在使用前
仍要过形态检查（内核地址域 + 8 字节对齐）。

**于是"建表阶段要不要 slide"这件事要记准，容易记反**：换算表里那几个量
（`gVirtBase` / `gPhysBase` / `ptov_table`）要用**符号的运行时地址**才读得到，而运行时
地址 = 链接期 vmaddr + slide（`KernelSlide.m:1381`、`:1073`）—— 不知道 slide 就不知道该
kread 哪个地址。所以建表阶段**确实依赖 slide**，面板上"先建立换算表、再建窗"是数据依赖，
不是摆放问题。

"physrw 不需要 slide"只对**最后那一步**成立：窗口建好、自映射写完之后，用普通 `str` 改
PTE、本地 `memcpy` 读物理内存，全程不需要换算也不需要 slide —— 那才是这条路的收益。
`km_phystokv_ensure()` 的作用是把这一步藏进入口（下游不必知道按钮顺序），本轮它与
`km_slide_resolve()` 可观测行为相同。

### 附：样本的 physrw 换算链（2026-09-26 反汇编定案）

**结论：样本用形态 B —— 纯线性公式 `va = virtBase + (pa − physBase)`，不查 `ptov_table`。**
与我们 `km_phystokv` 的兜底支逐字相同，这是一次独立验证。

1. **换算不在独立函数里，而是 ObjC block 的 `invoke`。** `__got[0x101B68408]` = `__NSConcreteStackBlock`；
   代码在栈上构造 0x40 字节 block，`invoke` = `0x10104954C`（读）/ `0x101049A10`（写，dst/src 互换）。
   所以 `[+0x20]~[+0x38]` 是 **block 的 captured variables**，不是结构体字段（前一轮把它们当结构体读了）。
2. 反编译形态：`memcpy(dst = a1[5] + (a1[4] & ~a1[6]) - (a1[6] & ~a1[4]), …)` ——
   `(x&~y)-(y&~x)` 是 OLLVM 的 MBA 恒等式（≡ `x−y`）。
3. `virtBase` / `physBase` 来自 `sub_1010490FC` 开头两条 mov（`x21 = x1` 是 virtBase、`x20 = x0` 是 physBase）。
   该函数被注册进 BSS 全局 engine `0x101D22888+0x10`（注册点 `sub_10104DBC8` 的 `10104DC24`），
   调用方式是 `ldr x8,[engine+0x10]; blr x8` —— **这就是"bl 交叉引用全为 0"的机制性原因**。
   同结构 `+0x50/+0x58` 由 `sub_101048D70` 写 `{0x101048C40, 0x10104874C}`（后者即窗口准备）。
4. **形态 A 被全局排除**：全二进制"同时含 `cmp #8` 与 24 字节步长"的函数 = **0 个**；
   无 `ptov_table` 字符串；无任何 `0xffff…` 形态的 movz/movk 常量（所以那两个基准**不是立即数**）。
5. **未确证**：`sub_1010490FC` 的 x0/x1 实参来源（间接 `blr`，调用点未定位）。
   日后若要闭环，最值钱的搜法是：找 `ldr x8, [xN, #0x10]` 且 xN 指向 `0x101D22888/0x101D22898`。
   另一组更快的入口：`0x100F950F4 bl 0x10104F7B0`、`0x100F953DC bl 0x101050BF4`、
   `0x100ECAD38` / `0x100ECC37C bl 0x10104DED0`、`0x100F95400 bl 0x101048C40`。

**一条必须记住的前提纠正**：`music样本`（`Music_unpack/…/Music`，345,366,864 B）**没有** `LC_DYLD_CHAINED_FIXUPS`，
它只有 `LC_DYLD_INFO_ONLY`（`rebase_off=0x1CE4000`）。chained fixups 属于**另一个样本** `Music_unpack2`（345,437,664 B）。
所以"必须解 chained fixups 才能搜到指针"这个说法对目标样本**不成立**，别再按它设计搜法。

```
0x101049068  orr  x21, x20, x8             ; x21 = 物理地址 | 模板
0x10104908c  and  x10, x8, x20
0x101049090  orr  x8, x8, x20
0x101049094  madd x8, x8, x10, x9          ; 槽位间距（编译器展开的 2 的幂距离）
0x10104909c  str  x21, [x8, w22, uxtw #3]  ; ★ PTE 写入：普通 EL0 索引存储
0x1010490a8  dmb  sy                       ; ★ 与 physrw_pte.c 的 __asm("dmb sy") 同位置

0x10104ce24  mov  x21, #0xe43
0x10104ce28  movk x21, #0x60, lsl #48
0x10104ce2c  orr  x1, x25, x21             ; 同一模板
0x10104ce30  mov  x0, x25
0x10104ce34  bl   #0x10104f800             ; ← 8 字节写原语（= physrw_pte.c:140）

0x1010524e8  mov  x27, #0xe43
0x1010524ec  movk x27, #0x60, lsl #48
```

`0x101049020` 起是 **`acquire_window` 的"找空槽"循环**（`w22` 从 2 起，`str xzr, [x8, x22, lsl #3]`）。

### 原语注册与分派（接上本文件上面那两份记录）

```
physrw_pte 初始化  0x10104DB94
  str x19, [G+0x880]                     ; G[0x880] = 窗口基址（Dopamine 的 gMagicPT）
  stp 0x1010490FC, 0x1010495A8, [G+0x898] ; G[0x898] = 读，G[0x8A0] = 写
0x10104f800（8 字节写）→ bl 0x10104e8c0 → ldr x8,[G+0x8a0] / br x9
0x10104f878（8 字节读）→ bl 0x10104ed7c → ldr x8,[G+0x888] / br x9
```

`ldr x8,[engine+0xNN]; br x9` 这种运行时函数指针分派，就是本文档上面记录的
"bl 交叉引用全为 0" 的机制性原因。

### flush_tlb 也在，且只在 init 里

```
0x101048e5c  ldr  x8, [x19, #0x880]   ; 取窗口基址
0x101048e60  strb w20, [x8]           ; 改 sw_asid 字节
0x101048e64  dmb  sy
```
与 `physrw_pte.c:19-29` 的 `*gSwAsid = fakeSwAsid; dmb sy; usleep(0); *gSwAsid = orig; dmb sy;`
逐句对应。**数据通路里不调它**——与 Dopamine 一致。

### 与 Dopamine 的唯一差异

窗口基址是**运行时算出来的，不是固定常量**。对 `0x7000000000` / `0x3FC0000000` / `0x8000000000`
做逐寄存器 movz/movk 链合成扫描，**全部 0 处**。它存在 `G[0x880]`，由建窗代码写入。

### 方法论的坑（必须记住）

**"扫不到某个立即数"不等于"这个常量不存在"。** 上一路扫描用的模式清单是
`0x407/0x40F/0x403/0x40B/0xC07/0x1C07`，而样本用的是 **`0xe43`**——不在清单里，
于是扫出 0 命中，被读成"没有 PTE 写入"。另外它看到 `bl 0x101093820`（取 page_size）
就判成"页尺寸乘法、与页表无关"——那个 `bl` 的真实作用是给 `madd` 提供页掩码。

**正确做法（本轮用的）**：拿一个**已知在用的常量**（叶模板）当锚点做全量命中，
再逐条 capstone 解上下文。不要拿"我以为的合法值清单"去扫。

## 面板与上机步骤（2026-09-26 精简后）

面板现在 **8 个按钮**：`刷新 / XPF / Slide / 建窗 / 表预检 / 建表 / 测偏移 / 读页`。

**删掉的 11 个**（世界/自己/玩家/对象/枚举/跑一次/映射/窗口/崩溃文件/内存/自动）分两类，
都不是"暂时不用"：
- 九个走 `MemoryProbe` → `km_read_process`，而那条读路**已废**：`g_linear_map_valid`
  在设备上稳定 resolved 成 `linear=unresolved`，`km_read_process` / `km_translate`
  入口一律直接失败（`KernelMemory.m:1642`、`:2066`、`:2161`）。留着它们的代价是
  每次上机都要先分辨"点了没反应"是坏了还是本来就不通。
- 两个（崩溃文件/内存）与读内存链无关。

**「刷新」不能删**：`reload()` 调它，而 `reload()` 是 `RootViewController.swift:115`
在面板重现时调的外部入口。

### 上机顺序（第一次验证数据通路）

1. 装最新构建（CI 产出的 `.tipa`）→ 开 App。
2. 点 **「建表」**。它内部会按需跑 `km_phystokv_ensure()`（首次几十秒解析 kernelcache，
   是预期耗时不是卡死）。成功判据：状态行出现「建表 + 自映射」字样，
   `km_physmap_magic_pt()` 非 0。
3. 点 **「读页」**。它读的是**自映射页表页本身**（`magicPT`），并做一条可判定核对：

```
读回的前 8 字节 == magicPT | 0x6000000000000e43 ？
```

`magicPT` 是那张页表页的物理地址，而该页已被自映射进本进程地址空间 —— 所以它的
第 0 个 8 字节就是自映射项自身。**这一个等式同时钉住三件事**：
PTE 已写入、窗口可从 EL0 直访、窗口地址正确。任何一环不成立，值都对不上。

- 显示 `✓ 自映射项核对一致` → 数据通路通了。
- 显示 `✗ 不一致` → 把那一行和摘要一起回贴。
- 摘要以「读页失败」开头 → 看它指出的是 acquire 环还是数据读取环。

### 一处仍未闭环的假设（真机首跑要盯的）

**EL0 直访那个窗口到底 fault 不 fault。** 页表项的权限是
`PERM_TO_PTE(PERM_KRW_URW)`（含 `AP[1]=1`）+ UXN/PXN=1，理论上 EL0 可读写，
但**真机没跑过**。真 fault 的形态是 **App 崩、不是内核 panic**（页表项本身是内核写
且有回读核对），崩溃点会直接指出卡在哪一步。

### 槽位缓存（这一轮加的，2026-09-26）

`kpm_slot_choose` 原先每次 acquire 要把 2048 个槽线性扫两遍（最坏 4096 次内核读，
每槽一次 `km_read64` = 两次 `kread`）。现在加了一层 16 条 `(pa, slot)` 缓存做快路径，
热路径（反复读同一片物理页）降到**一次验证读**。

**这层缓存是纯建议性的**：每次 lookup 都回读槽位、比对
`(v & KM_PM_TTE_PA_MASK) == pa`，条目过期就落回全表扫描，不会产出错误映射。

**唯一能出严重错误的地方是「全清」**：`kpm_slot_choose` 第 ③ 支把 2..2047 全清之后，
缓存里每一条都可能指向一个已被别人占用的槽。所以 `kpm_slot_cache_clear()` 落在
`.m:1339` —— **在清写循环的第一笔之前**，不是循环之后，这样连"清到一半中止"也覆盖。
**改这一段之前先读那一段注释。**

### TLB 陈旧：这条链靠什么成立（别把它当 flush_tlb）

`kpm_window_data_sync()` 是 `usleep(0) / __sync_synchronize() / usleep(0)` 三句，
形态照 `physrw_pte.c:66-69`。**它不保证什么**，这一点写在 `.m:1474-1493`：

- 架构上**没有任何条款**保证 `usleep(0)` 使旧翻译失效（它只是让出 CPU，调度器可以
  立刻把同一线程放回来）；`dmb sy` 也不导致翻译失效。
- Aether **没有** Dopamine 的 `flush_tlb()`（那要靠 `gSwAsid`，而 `sw_asid` 偏移
  本身是没真机确证的值 —— 不去用它）。

**真正承担正确性的是「同一个 pa 再来时不重写映射」**：`kpm_slot_choose` 的 ① 支与缓存
快路径都会选回原槽，`kpm_slot_write` 读到 `old == value` 便一个字节都不写 ——
没有新写，就没有"新写的项与旧 TLB 条目不一致"这个窗口。

**真机若复现「读到陈旧内容」**，第一处查 `kpm_slot_choose` 第 ③ 支全清之后那一段：
先在窗口诊断里找 `how` 为「全清后从 2 起」的记录（确认那一支真执行过），再看清完后
第一次读回来的是什么。

## 两条内核读路径：delta 不同，页首可读性不同（2026-09-27）

这是本工程最容易反复踩进去的一个坑，所以单列一节。

底层读原语的机制：把一个本进程持有的内核对象的**指针字段**改写成 `kaddr − delta`，
再让内核按内核语义从那个指针开始解引用。**两条路径的 delta 不同**，于是"能不能读页首"
也不同：

```
64 位  kread_sem_open.h:147   delta = offsetof(pseminfo, psem_uid)      = 0x0C
                              → 源访问最低到 kaddr − 0x08  → 页首会踩前一页 → 整机 panic
32 位  kread_sem_open.h:175   delta = offsetof(pseminfo, psem_usecount) = 0x04
                              → 源访问从 kaddr 本身开始    → 页首可读
```

**为什么 32 位那条不踩前一页**（这一条来自外部复核，本仓库无法自行验证，因为不含 XNU 源码）：
公开 XNU 的 `fill_pseminfo()` **不读 `pinfo + 0`** —— 第一个字段 `psem_flags` 的检查被
`#if 0` 关掉了；它逐字段读，最低的源访问地址是 `pinfo + 0x04`。对 32 位路径，
设目标 `A`、`pinfo = A − 0x04`，最低源访问 = `A`，整个源访问包络是 `[A, A + 0x30)`，
**完全不含 A 之前的任何字节**。

**一个容易算错的细节**：返回结构里 `vst_size` 位于 `psem_fdinfo + 0x70`，但这**与内核读哪个
地址无关**。那条赋值是 `sb->vst_size = pinfo->psem_usecount;` —— 源是 `pinfo + 0x04 = A`，
目标才是返回结构的 `0x70`。所以 delta 就是 `0x04`，**不要**改成 `0x70`。

因此本工程现在有两条路径：
- `km_read` / `km_read64`（64 位，闸门要求页内偏移 ≥ `0x0C`）—— 主体读路径；
- `km_read_u32`（32 位，闸门按整段 `[addr, addr + 0x30)` 落在页内，**下界为 0**，
  只要求 4 字节对齐）—— 专门用于"读页首"这类访问。

### 由此修好的一件事：`kernel_base` 自检

自检原本读 `kernel_base + 0x10` 的 `ncmds` / `sizeofcmds`，**那是被迫的弱判据**——因为
64 位路径读不了页首。现在改用上游 `perf.h:112-118` 的**强判据**，走 32 位路径：

```
km_read_u32(kernel_base)     期望 0xfeedfacf  (MH_MAGIC_64)
km_read_u32(kernel_base + 4) 期望 0x0100000c  (CPU_TYPE_ARM64|CPU_ARCH_ABI64)
```

**两条必须记住的限定**（写在 `slide_verify_kernel_base` 上方）：

1. 这条自检**不能验证候选基址是否正确**。候选页未映射时它照样 panic —— 它只是把
   "读页首这件事本身"变成可行的，不是把错地址变成对的。
2. `0x30` 这个包络只覆盖到 `psem_name` 末尾。若内核还会读 `pseminfo` 更后面的字段
   （`psem_semobject@0x34` 等），真实包络更宽。那是**页尾方向**，而 64 位路径的上界
   （`0x28`）比它还紧，所以本次没有让这个方向变差。

### 仍未解决的一件事：`slide` 偏了 133 MB

一次 panic 日志给出了权威值（同一次启动）：

```
KernelCache base = 0xfffffe0019b08000     KernelCache slide = 0x0000000012b04000
Kernel text base = 0xfffffe0019b10000     Kernel slide      = 0x0000000012b0c000
Kernel text exec base = 0xfffffe001aa60000
```

三组"base − 自己的 slide"全部等于 `0xfffffe0007004000`，**即我们用的链接基址完全正确**。
而我们推出的 slide 是 `0xa594000`，比真实的 `0x12b04000` 少 `0x8570000`（133 MB）。

**偏差 100% 来自 slide 的推导**（`slide = vn_kqfilter 运行时 − vn_kqfilter 链接期`），
链接基址不承担任何误差。成因未定，候选假设（按排查优先级）见
`docs/提问-读原语触发panic归因.md`。

**在这一条修对之前，任何依赖 slide 的内核读都可能踩空。** 上机前先看这里。
