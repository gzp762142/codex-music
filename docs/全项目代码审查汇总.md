## 零之二、彩屏的完整根因链（P0，可静态证明）

这条链由内核层审查独立挖出，是本次审查最重要的产出。**它不是参数问题，是一条必然失败链。**

### 触发源：`dynamic_info.h` 22.4.0 表项的字段自相矛盾

```
[#3] Darwin 22.4.0   perf_supported=true    kernelcache__* 全为 0    ← 唯一自相矛盾
[#4] Darwin 22.5.0   perf_supported=true    kernelcache__* 8 项非零   ✔
[#5] Darwin 22.6.0   perf_supported=true    kernelcache__* 8 项非零   ✔
```

同一条目的注释（`L118-119`）写着 *"kernelcache__* 按本表开头的约定留 0：本工程靠扫描找内核基址，**不读 perf 的静态地址表**"*，
而 `L125` 却写着 `.perf_supported = true`。**两者不可能同时成立**，而 `perf_run()` 的唯一守卫只认后者：

```c
// perf.h:92-94
if (!kern_versions[kfd->info.env.vid].perf_supported) { return; }
```

### 失败链

```c
// perf.h:106-110
u64 vn_kqfilter  = UNSIGN_PTR(fo_kqfilter);
u64 kernel_slide = vn_kqfilter - dynamic_info(kernelcache__vn_kqfilter);  // 减 0
u64 kernel_base  = ARM64_LINK_ADDR + kernel_slide;                        // 溢出回绕
// ARM64_LINK_ADDR = 0xfffffff007004000  (static_info.h:12)

// perf.h:114
mh_header[0] = kread_sem_open_kread_u32(kfd, kernel_base);   // 打在未映射内核地址上
```

`kopen` 的执行顺序：

```
puaf_run → krkw_run → info_run → perf_run(此处失败) → puaf_cleanup(被跳过)
```

`libkfd.h:182-189`。**`perf_run` 一失败，`puaf_cleanup` 就永远不执行** —— 于是 `vm_map` 带着未清理的 PUAF 残留交还给调用方。

上游 `smith.h:131-134` 的原文正是判据：
> cleanup 是回到 safe state 唯一必需的事，否则进程退出或做任何 VM 操作都可能内核 panic。

### 放大器：同一次会话引入的重试

`kfd_try_open` 原本失败后重试 3 次，每次只 `sem_unlink`（清不掉内核侧残留），再跑一整轮 landa
（5 个 `vm_allocate` + `vm_remap` + `vm_copy` + `vm_deallocate`）→ **在已损坏的 `vm_map` 上插入新 entry** → 两个相同 start →

```
VMSEL: INSERT FAILED: 0x10b000000, 0x10b800000, 0x10b000000, 0x10b1a8000
                     ↑新条目start   ↑新条目end   ↑已存在start ↑已存在end
```

**重试机制是净负面的放大器，不是安全网。**

### 为什么设备以前没崩

`_backup` 里的旧 `dynamic_info.h` **根本没有 22.4.0 条目**。旧快照在 16.4.1 上会停在
`info_init` 的 `assert_false("unsupported osversion")` —— 那一步在 `puaf_run` **之前**，所以是安全失败。

**是新增的 22.4.0 表项把设备"解锁"进了崩溃路径。**

## 一、本次会话已修复（5 项，全部由审查发现）

### 1. `KernelMemory.m` `kfd_try_open` 的 3 次重试 —— 我引入的风险，已移除

**两位独立 agent 各自指到同一条，且都判为"三次彩屏最强解释"。**

原实现：`for (attempt = 0; attempt < 3; attempt++)`，失败后只 `sem_unlink("kfd-posix-semaphore")` 就再跑一次 PUAFF。

**问题**：`sem_unlink` 只清用户态 semaphore 名字，**清不掉内核侧 PUAFF 残留**（悬空 PTE、半裁开的 `vm_map` 条目）。在残留之上再跑一次 PUAFF = 对已经不一致的 `vm_map` 再插一次。**失败概率是累积的，不是三次独立事件。**

**已改为**：一次失败即终止本次会话，只做 `sem_unlink` 清理后返回 0。想重试交给下次进程启动（那时 `vm_map` 干净）。

### 2. `KernelMemory.m:381` `g_handle` 过早发布 —— 已拆成两个标志

原实现 `g_handle = handle;` 之后还要跑 `km_scan_kernel_base`（最多 4096 次 kread）与 `km_locate_linear_map`，而 `km_ready()` 那一刻就返回 `true`。

**问题**：别的线程可在此期间并发进入 `km_read` / `km_proc_for_pid`，而 **libkfd 后端非线程安全**：

- `kread_sem_open.h:142-148` 每次读都改写自己 psemnode 的 `pinfo`
- `kwrite_sem_open.h:14` 把 kwrite 的方法缓冲**指向 kread 的同一块内存**
- `kwrite_dup.h:101-127` 的内核写目标由本进程 `fileproc.fp_guard` 推出 → 并发踩踏即写到非预期内核地址

**已改为**：新增 `static bool g_kernel_ready`，`km_ready()` 返回 `g_kernel_ready && g_handle != 0`；`g_kernel_ready` 只在 `km_init` 全程走完后置位，`km_deinit` 先撤标志再 `kclose`。

### 3. `km_self_test` 的 PTE 写回 —— 已改为只读（上一轮）

删除了 `km_write(pte_kva, &before, ...)`。理由：PTE 值含 PA+权限位，写偏即凭空造错配映射；且 `after == before` 判据证明不了写入生效。

## 二、待修：与彩屏同源的高危项

### 4. `MemoryProbe.swift` 自映射 —— 两位 agent 独立确认

`mapRange:358-359`、`mapAllRegions:507-508`、`mapRegionContaining:448`、`nextRegion:2737`、`stepFindBase:2830` 全部把 `mach_task_self_` 当目标进程用：

```swift
let rk = fn(mach_task_self_, &target, total, 0, vmFlagsAnywhere,
            mach_task_self_, aligned, 0, &curProt, &maxProt, 0)
//          ↑ target_task = 自己      ↑ src_task = 自己
```

代码注释自承："端口机制已移除……这里退化为对本进程做 remap"。`mapAllRegions` 默认 `maxBlocks: 600` → 一次对**自己的 vm_map** 插 600 次，与 `vm_map_store_rb` 插入路径同型。

**但顺序上它不是 23:26 那次的元凶**：`readSmart:602` 被 `if AppDelegate.kernelReady` 门控，而 `kopen` 尚未返回时该标志仍是 false。它是**待触发**的第二个雷。

附带两个真实缺陷：
- `vm_remap` 会按源 region 边界**截短**映射，代码却按请求的 `total` 记账 → 失败路径 `mach_vm_deallocate(target, total)` 释放面积大于实际映射，**连带释放相邻区间**（本进程 SIGSEGV）；成功路径把不存在的区间写进 `mappedRanges`，`readSmart` 从里面读垃圾且**不回退**内核读。
- `releaseAllMappings:314` 在 `vmDeallocateFn == nil` 时只清记录不释放，而 `bind(pid:)` 会调它，`bind` 有两个调用线程 → `mappedRanges` 无锁竞争。

### 5. `AppDelegate.swift:50` 失败也置 `kernelReady = true`

`kernelReady` 真实语义只是"`km_init` 已返回"，但 `MemoryProbe:602` 拿它当"内核层验通"的开关。**`km_init` 失败时反而会启用自映射快路径**，并叠加 `mlock` 整块 → 8GB 设备上的 jetsam 压力。

### 6. `kernelReady` / `kernelNote` 跨线程非原子访问

`kernelNote` 是 `String`（堆缓冲 + ARC），后台队列写、主线程 `DebugProcView:282` 每秒读 → UB，可随机崩溃。`kernelReady` 虽是 Bool，但"置位放最后"在无屏障下不构成 happens-before。

### 7. `km_init` 幂等守卫只看 `g_handle`

`if (g_handle != 0) return true;` —— 失败后 `g_handle` 保持 0，下一次调用会把整轮 PUAFF 再跑一遍。应改为看 `g_kernel_ready`。

## 五、已核对无误（可放心）

- **Swift 层没有任何 `km_write` / `km_write_process` 调用点** —— 唯一触达内核的原语是 `km_read_process`（只读）。「Swift 层写内核」整类可排除
- **C 层 `km_write` / `km_write_process` 也是零调用点**（`km_self_test` 里那次 PTE「原值写回」已在上一轮删除）—— 即 Aether 侧不存在活跃的内核写调用链。libkfd 自己的 `kwrite` 只在 `kopen`（POKEN / dynamic_info 握手）内部被调用，属于库自建原语，本工程不额外调用
- **库级守卫齐全**：`km_read` / `km_read64` / `km_write` 有 `g_handle == 0` 与 `km_is_kernel_address` 检查；`km_translate` / `km_read_process` / `km_write_process` 有 `g_linear_map_valid` 检查；`km_self_test` 的 PTE 自检入口也补上了 `g_linear_map_valid`
- **`km_locate_linear_map` 的置位来源已收紧**：`g_linear_map_valid` 只在「walk 出一次真实 (VA, PA) 观测」的路径上置 true；`km_bootstrap_linear_delta`（pmap 的 `tte − ttep`）退化为**纯诊断读数**，不再置位（理由见下条）
- **无强引用环**：`FangUIBridge` 的 Timer/observer/闭包、`RootView`、`DebugProcView` 均弱引用并自行 invalidate
- **`km_route` 返回值契约**：`readAt`/`readRaw`/`readBytes` 失败时返回 `(kr, 0)`，不返回脏值
- **偏移计算**：`stepPlayers`/`stepWorld`/`readText`/`readNameDetail` 的访问偏移逐个核对，未发现越界
- **`ProcessScanner.rawSysctlList`**：指针不逃逸闭包，`count` 二次计算正确
- **无 task port / send right 泄漏**：`task_for_pid`、`mach_vm_read` 已无实际调用
