## 一、平台与读原语（全部为已核实事实）

- 平台：iPad14,3 / socId 8112（T8112）/ iOS 16.4.1 (20E252) /
  Darwin 22.4.0 / xnu-8796.102.5~1 / **arm64e** / **16 KB 页** / 无越狱。
- 语言：Objective-C（**MRC 编译单元，非 ARC**）+ C。工程无本地编译能力，只能靠 CI（GitHub Actions / macOS-14）。
- 内核读原语：libkfd 的 `kread_sem_open` 后端。原理是**把本进程持有的一个内核对象的
  指针字段改写成 `kaddr − delta`**，再让内核按内核语义从那个指针开始解引用，
  把结构体拷回用户态。
- **没有 fault-recovery**：踩未映射地址 = 内核态 same-EL data abort = 整机 panic。
- 两条路径的 delta（已实测）：
  - 64 位路径 `delta = 0x0C` ⇒ 内核最低源访问地址 = `addr − 0x08`；
  - 32 位路径 `delta = 0x04` ⇒ 源访问从 `addr` 本身开始（**页首可读**）。

## 二、现状：读路径目前是死的，且这是刻意为之

### 2.1 主线的死锁（已写在代码注释里）

`KernelMemory.m` 的 `km_read_process()` 是当前唯一的进程内存读取入口：

```
km_read_process(pid, uaddr, out, len)
  ├─ 入口闸门：g_linear_map_valid 必须为 true，否则直接 false
  ├─ km_translate(pid, uaddr, &pa)
  │    ├─ km_proc_for_pid(pid)                    ← 问题 ②
  │    ├─ task = proc + proc__object_size
  │    ├─ map  = read64(task + task__map)
  │    ├─ pmap = read64(map + offsetof(_vm_map, pmap))
  │    └─ km_page_table_walk(pmap, uaddr, &pa)
  └─ kva = pa + g_linear_delta                     ← 问题 ①
     km_read(kva, …)
```

`KernelMemory.m:2179-2190` 的注释明确记录了结果：

> 本次止损之后，下面四条基于 walk 的路由在设备上会**稳定失败**……
> 也就是一个闭环。最终稳定落在：`valid == false`、`delta == 0`、
> `km_read_process / km_write_process` 一律直接失败。

闭环的形状：

```
km_page_table_walk 的下钻要求 g_linear_map_valid == true
g_linear_map_valid 只能由四条 km_compute_linear_delta 路径置位
那四条路径内部要调 km_page_table_walk
→ 互为前提，永远不可能同时成立
```

`DebugProcView.swift:96-101` 也据此**删掉了九个按钮**，理由写着"那条读路已经作废"。

### 2.2 但另一条链是活的，而且已经被完整实现

`KernelSlide` / `KernelPhysWindow` / `KernelPhysMap` 三个模块**都不依赖**
`g_linear_map_valid`，它们走的是 `km_phystokv()`：

```
km_phystokv(pa)
  ├─ ① 查 ptov_table 的 8 段：命中返回 pa - entry.pa + entry.va
  └─ ② 落空退回 pa - gPhysBase + gVirtBase
        （且要求 pa ∈ [gPhysBase, gPhysBase + gPhysSize)）
```

`km_phystokv_ready()` / `km_phystokv_ensure()` 负责按需建立这套换算（`KernelPhysWindow.m:469-473`
已经改成"按需 ensure"，不再要求用户先点 Slide）。

`KernelPhysMap` 已经提供了完整的物理读写：

```
bool km_physmap_physreadbuf (uint64_t pa, void *out, uint64_t size);
bool km_physmap_physwritebuf(uint64_t pa, const void *in,  uint64_t size);
bool km_physmap_acquire_window(uint64_t pa, void (^block)(uint64_t ua));
```

它做的是：**自建一张页表页 → 建立自映射 → 用普通 EL0 写指令把目标物理页的 PTE 填进去
→ 然后在用户态直接读那块窗口地址**。全链只有初始化时 flush 一次 TLB，之后不再发 kcall
（Dopamine 的 `physrw_pte` 家族做法）。

**关键事实**：`MemoryProbe.swift`（UI 层唯一的内存读取实现）**完全没有调用**
`km_physmap_*` / `km_physwindow_*` / `km_phystokv` —— 一条都没有。
所以"能读物理内存"和"能读目标进程内存"这两件事目前是**断开的**。

## 三、要做的事：把两条链接起来

### 步骤 1：用 `km_phystokv` 替掉 `pa + g_linear_delta`（解开死锁）

**这是最小改动、收益最大的一步。**

`km_translate()` 走完页表遍历后已经拿到了目标用户页的**物理地址 `pa`**。
现在它把 `pa` 交给调用方，调用方做 `pa + g_linear_delta` 当 KVA 去 `km_read`——
而 `g_linear_delta` 因为闭环永远是 0。

改成：**用 `km_phystokv(pa)` 求 KVA**，然后 `km_read64(kva, …)`。

- 为什么可行：`km_phystokv` 是独立实现（ptov_table / gPhysBase+gVirtBase），
  它的正确性由 `KernelSlide` 的 ⑥⑦ 步自检保证，**与 `g_linear_map_valid` 无关**。
- 为什么安全：`km_phystokv` 内部要求 `pa` 落在 `[gPhysBase, gPhysBase + gPhysSize)` 内
  （上游把这条写成 assert，本工程改成返回值判据），落空时返回 0 / 明确失败 ——
  **不会返回一个"看起来合法的错值"**。
- 请给出：`km_translate` 与 `km_read_process` 的完整修改后函数体；
  并明确 `km_phystokv` 返回 0 时的处理（必须停在失败，不许退回任何兜底）。
- **注意**：`g_linear_map_valid` / `g_linear_delta` 这套机制**不要删**——
  在它没有被证明永远不可用之前，保留原路径作为可对照的第二实现。请只做"新增一条
  可用路径并优先走它"，不要顺带清理。

### 步骤 2：数据面改用物理窗口（可选但强烈建议）

步骤 1 之后，每次读一页要发一次 `km_read`（走 sem_open，慢，且每次都要写内核对象
的指针字段）。而 `KernelPhysMap` 已经能在用户态直接读物理页。

**请评估并实现**：让 `km_read_process` 的数据面走
`km_phystokv(pa)` → 窗口 → EL0 直读，而不是 `km_read`：

- 收益：一个页表页建立后，每次读不再修改内核对象状态，速度与稳定性都远好于 sem_open。
- 风险：**EL0 直接访问那块窗口地址这件事，在本设备上从未被验证过**。
  `KernelPhysMap.h` 里那个「读页」按钮就是为验证它加的（把自映射的页表页当普通内存
  读一页回来，核对第 0 个 8 字节）。
- 请给出：如何**先验证窗口可用、再切数据面**的顺序（先跑通「读页」那条自检，
  再让读取走窗口）；以及窗口不可用时如何干净地退回步骤 1 的路径。
- 如果这条做不到，请说明卡在哪，不要硬写。

### 步骤 3：目标进程的定位（当前被编译期开关停用）

`km_proc_for_pid(pid)` 目前只有 self pid 短路：

```c
if (pid == kfd->info.env.pid && current_proc) {
    return current_proc;     // 只有自己
}
// KM_ENABLE_PLIST_WALK == 0 ⇒ 其余 pid 一律 return 0
```

要读写**目标进程**（不是自己），必须恢复"按 pid 在进程链表里定位 proc"。
`KM_ENABLE_PLIST_WALK=0` 的停用理由是：跳转时读出来的指针**没被证明已映射**，
可能落在内核空洞里从而触发 panic。

**请实现一个安全版本**，要求：

- 从已知锚点出发：`kernel_proc`（内核里 allproc 的起点）或 `current_proc`。
- 用 `p_list` 链定位：`proc__p_list__le_prev`（本机版本表 = `0x0008`）、
  `proc__p_pid`（= `0x0060`）。
- **每一步的地址都必须能回溯到「已确认对象 + 已知字段偏移」** —— 这一点请你论证，
  而不是假定。特别地：链上读出的 `le_prev` 只是个指针值，用它拼下一次读地址时，
  它属于"读出来的值当地址用"。请说明在什么前提下这是可接受的，
  以及**怎么在拼下一次地址之前先证明它落在已映射区**（这是恢复这条链的核心难点，
  也是它当初被停用的原因）。
- 必须有的护栏：最大跳数、形态检查（高 16 位 `0xFFFF` + 8 字节对齐 + 非 0）、
  遇到形态不合立即停（返回 0，**不重试、不换偏移**）。
- 本机的进程数在数百量级，pid 为 4 位数。

**如果你认为恢复 `p_list` 遍历无法做到"每步都已被证明映射"，请直接说，
并给出替代方案**（例如：能否用别的、可证明已映射的锚点链？）。

## 四、硬约束（违反任一条 = 整机重启，不可协商）

1. **零盲读**：送进读原语的地址必须能回溯到「已确认对象 + 已知字段偏移」。
   不许"猜一个地址然后读它"，不许"读失败就换个偏移再试"。
2. 每一步过形态检查：内核地址域（高 16 位 `0xFFFF`）+ 8 字节对齐 + 非 0。
3. **失败就停**：不许用兜底常量把失败包装成成功，不许静默重试。
4. 诊断文本永不返回 nil；`%#llx` 的实参一律强转 `(unsigned long long)`；
   定义必须在使用之前（C 无前向引用）。
5. 只读模块不许有写操作。
6. 不改这三个模块的对外头文件签名：`KernelSlide.h` / `KernelPhysWindow.h` /
   `KernelPhysMap.h`（面板按固定签名调用）。

## 五、页闸门（写读代码时必须遵守的地形）

16 KB 页。64 位路径的读取要求每个 8 字节字满足：

```
页内偏移 >= 0x0C  且  末字节 <= 页大小 − 0x28 − 1
```

写路径：`>= 0x08` 且 `<= 页大小 − 0x08 − 1`；32 位路径：上界 `0x30`、无下溢要求。

**注意**：结构字段偏移不总是 8 的倍数。当某字段落在 8 字节字下沿时，
必须从 `addr − 8` 起读再取高 4 字节。32 位路径（`km_read_u32`）没有下溢限制，
**页首可读**——这正是「读 Mach-O 头」那类地址只能走它的原因。
