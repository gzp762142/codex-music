# 样本读取路线图 —— 从进程启动到读出目标内存

> 对象：`D:\工作区\music样本\Music_unpack\Payload\Music.app\Music`
> （345,366,864 B，thin arm64e，已 strip，cryptid=0）
> 依据：`_analysis/` 下三份实测报告 —— `physrw样本全链报告.md`、
> `样本_内核基址获取链_实测.md`、`样本读取路径.html`。
> **凡本文写出的地址、常量、指令，都在那些报告里有字节级复现命令；未测定的另注。**

## 零、先纠正三个此前流传的错误结论

在讲路线之前必须先把它们清掉，否则后面的理解会整体歪掉。

| 曾经的说法 | 实测结果 |
|---|---|
| 样本走 Dopamine 的 `physrw_pte`（自建页表 + 写 PTE + 自映射） | **不成立**。样本**不构造页表、不写 PTE、不建自映射窗口**。全 `__text` 搜 PTE 权限位立即数（`0x407/0x40F/0x403/0x40B/0xC07`）命中 17 处，**全部在 Apple 库代码里**，physrw 区域 0 处；无 `tlbi` 等 TLB 维护指令 |
| 自映射目标 VA `0x7000000000` | **样本里不存在**。4,370,633 条 `__text` 指令做 MOVZ/MOVK 立即数合成搜索，命中 **0** |
| 样本用 `ARM64_LINK_ADDR` 常量（`0xfffffff007004000` 或 `0xfffffe0007004000`） | **样本里一个都没有**。两种写法在整个 345 MB 文件里各命中 **0**。它不查静态偏移表、不做版本匹配 |
| 本工程"现在传 `copy = 1`，所以读到全 0" | **已过时，不要再用**。本工程**当前代码传的是 `copy = FALSE`**（`MemoryProbe.swift:642-643`，第 9 个实参为 `0`），并且已按样本逐步骤实现了建窗七步。`copy = 1` 是更早阶段的状态 |

顺带一条：样本**不调用 kcall**。全二进制只有 2 条 kcall 相关字符串，都是
`fugu14_kcall_init` 的失败日志；12 个 `kernelGadget.*` 键从未被解析。

## 一、总览：它的思路是"三段解耦"

样本读目标内存，做的**不是**一条长链，而是三段彼此独立的动作，每段各自求一个东西：

```
① 拿到内核读写能力         —— 靠 IOSurface 内核客户端（kread_IOSurface）
② 找到 kernel base         —— 靠"任意内核读" + 硬编码锚点 + 逐页扫 magic
③ 读写物理内存             —— 靠一对标量 (vaBase, paBase) 做线性换算 + 内核侧拷贝
④ 读目标进程内存           —— 两条并列路线：physrw（走③）与 vm_remap 共享映射（不走③）
```

**关键设计选择**：第 ② 段用的是**扫描**，不是**符号解析**。这是它与本工程
最根本的分歧点——本工程花了大半时间在 XPF 符号解析与 slide 求值上，
而样本把这一整类问题绕开了。

## 二、① 内核读写能力从哪来

入口不在"利用漏洞"，而在**接收**：

```
[physrw] lb_physrw_init: receivedHandoff=%d
```

样本带一个 `receivedHandoff` 机制 —— 内核读写原语是通过**交接**拿到的，而不是自己
从零打一条利用链。这条决定了它整条路线的性质：它站在一个已经成立的
内核读写之上。

具体实现是 **IOSurface 内核客户端**（kfd 血统）：

```
kread_IOSurface_init          ← 字符串实测在 0x101CBA2E0
IOSurfaceRoot                 ← 0x101CB63D6
IOSurface.c / IOSurface_shared.h
```

运行路径经 **Mach trap**：`0x100FA2B88` 是 `mach_msg_trap`（`mov x16,#0x14; svc #0x80`）
的包装器，紧随其后 `0x100FA2BCC`（trap `#0x27`）、`0x100FA2C10`（trap `#0x14e`）
是同一批。**它走的是用户态 trap 到内核的常规通道，不是 svc 直调内核符号。**

拿到能力后，它把原语函数指针**注册进一张全局表**（`__DATA,__bss`，`0x101D22880` 起）：

```asm
101048714  stp  x9, x10, [x8, #0x10]   ; [0x101D22898]=0x1010451D8 ; [0x101D228A0]=0x1010452AC
101048718  stp  xzr, xzr, [x8]         ; 前两个槽清零
```

后续一切读写都经由这张表间接调用：

```asm
10104E3CC  ...  ldr x8,[0x101D22898] ; cmp x8,#0 ; blr x8   ; 未注册则 mov w0,#-1
```

**思路要点**：能力与用途分离。表里存的是"能读写"这件事，谁来读、读什么，
由上层决定。所以同一份 physrw 既能服务自己，也能服务别的模块。

## 三、② kernel base：扫描，而不是解析

这是样本最值得单独讲的一段。

### 3.1 它不要符号表

已被实测否定的：`static_info.h` 那条路（版本表 + `ARM64_LINK_ADDR`）**被整条砍掉**。
不匹配 Darwin 版本、不读 kernelcache、不做 UUID 校验。

### 3.2 它怎么做

唯一入口 `0x100F9D08C`，调用点只有一处（`0x100F9C2BC`）。核心是一段反向扫描：

```asm
0x0100f9d1fc  add  x0, x0, #0x28                    ; 入参锚点 + 0x28
0x0100f9d200  bl   #0x100f98dc0                     ; mc_kread64(锚点+0x28)
0x0100f9d204  and  x20, x0, #0xffffffffffffc000     ; 页对齐（16 KB 掩码）
0x0100f9d210  sub  x20, x20, #4, lsl #12            ; 向下翻一页（减 0x4000）
0x0100f9d214  mov  x0, x20
0x0100f9d218  bl   #0x100f98d1c                     ; mc_kread32(该页首)
0x0100f9d21c  cmp  w0, w21                          ; w21 = 0xFEEDFACF
0x0100f9d234  b    #0x100f9d210                     ; 不等就继续减 0x4000
0x0100f9d24c  mov  x0, x20                          ; 命中 -> 返回该地址
```

即：**取锚点里 +0x28 处的指针 → 页对齐 → 向低地址每 16 KB 读 4 字节 → 命中
`0xFEEDFACF`（MH_MAGIC_64）就是 kernel base。**

锚点 `0xFFFFFFE3831F8000` 是**硬编码立即数**（`mov x1,#-0x8000; movk x1,#0x831f,lsl#16;
movk x1,#0xffe3,lsl#32`），不是从文件里读的常量池——所以字节级搜索搜不到它，
只能从指令里拼出来。

### 3.3 为什么这条路对样本成立、对本工程不成立

| | 样本 | 本工程 |
|---|---|---|
| 求 kernel base | 扫内存找 `0xFEEDFACF` | 解 XPF 符号 + 求 slide + 拼基址 + 自检 |
| 依赖 | 只需"能读内核" | 依赖 XPF 符号解析、链接基址口径、PAC 还原 |
| 失败方式 | 扫不到就一直扫（可能很慢） | 符号取错 → slide 偏 133 MB → 拼出未映射地址 → **整机重启** |
| 它没有的东西 | 没有 slide 概念 | slide 是整个工程的核心难点 |

**这是本次对照里最有价值的一条**：样本把"内核基址"这个问题的**输入需求降到了最低**——
它只要一个"任意地址读 4 字节"的能力，加一个够近的起点。
而本工程选择了符号解析路线，于是被符号口径、链接基址口径、PAC 三者同时绑住。

它付的代价是：需要一个**硬编码锚点**（`0xFFFFFFE3831F8000`），而且锚点 +0x28
那个指针必须本身就指向某个内核映像附近。这在本设备上是否可用、锚点该取什么值，
报告里没有定论——这是这条路唯一的硬依赖。

## 四、③ 物理读写：一对标量 + 内核侧拷贝

### 4.1 换算公式（实测指令）

**正向 pa → kva（读侧，`0x10104F2E8`）：**

```asm
10104F350  ldp  x8, x9, [x19, #0x30]   ; x8 = vaBase, x9 = paBase
10104F354  sub  x9, x21, x9            ; x9 = pa - paBase
10104F358  add  x1, x8, x9             ; x1 = vaBase + (pa - paBase)   ← pa → kva
10104F35C  mov  x2, x20                ; len
10104F360  bl   #0x10104e3cc           ; 内核侧拷贝(dst, src=x1, len)
```

**反向 kva → pa（`0x101048890`）：**

```asm
101048890  ldr  x8, [x20, #0x28]       ; paBase
101048894  sub  x8, x19, x8            ; x19 = kva
101048898  ldr  x9, [x20, #0x18]       ; vaBase
10104889C  add  x0, x8, x9
```

结构体布局固定：`[base+0x18] = vaBase`、`[base+0x20] = 输出对象`、`[base+0x28] = paBase`。
读侧版本把这对基址放在 `this+0x30` / `this+0x38`。

### 4.2 几个值得注意的细节

- **写侧插了一个会被抵消的常量**：`0x10104F3A8` 处先 `pa + 0xF93A151819B5F3C5`，
  再减同一个常量。算术上毫无作用，是**抗模式匹配的混淆噪声**。
- **有一处指针混淆（pointer mangling）**：`0x101045130` 做位折叠 + 64 位乘子 `madd` 混合，
  掩码 `0x7ffffff000000000` / `0xfffffff000000000` 取的是"第 36 位以上"，
  即剥离页内偏移与页表索引部分——与样本里 `xpf_find_pointer_mask` 同源。
- **热路径不做任何地址校验**：`0x10104F2E8` / `0x10104F3A8` 换算前只检查
  "ObjC 上下文非空"，对 `pa`、`len` 不查范围、不查对齐、不查溢出，直接交给内核。
- **唯一一处真正的范围判定**在 `0x101048818`–`0x10104883C`，形如
  `base <= pa < base+size`（`subs`/`cset hs`/`add`/`cmp`/`cset lo`/`eor`/`csinc`/`and`），
  但**不在读写热路径上**。

**思路要点**：它把正确性**寄托在内核侧**，自己不做输入校验。这与本工程"每步都过形态门、
不通过就停"的纪律正好相反——本工程这么写是因为踩错地址会整机重启，而样本这么写是因为
它那条路踩错最多是返回失败。

### 4.3 它解析的符号

虽然不用 `ARM64_LINK_ADDR`，但它仍然需要几个量来建立换算：

```
kernelSymbol.gPhysBase      0x101CCBF50
kernelSymbol.gPhysSize      0x101CD0D90
kernelSymbol.phystokv       0x101CCBCB0
kernelSymbol.cpu_ttep       0x101CD8710
kernelSymbol.vm_last_phys   0x101CCF540
```

还有一条 assert 字符串直接写出了它的判据：

```
!((pa < gPhysBase) || ((pa - gPhysBase) >= gPhysSize))
```

**这就是 `phystokv` 的前提条件**——与本工程 `km_phystokv` 落空判据是同一条。

## 五、④ 读目标进程内存：两条并列路线

### 路线 A：physrw（走 ③ 的物理读写）

上层先定位目标进程的内核结构：

```
[physrw] handoff: pid=%d
[physrw] proc=0x%llx
[physrw] task=0x%llx
[physrw_pte] vmMap=0x%llx
[physrw_pte] pmap=0x%llx
```

拿到 `task` / `vmMap` / `pmap` 之后，就能把目标进程的用户态 VA 翻成物理地址，
再用 ③ 的 `vaBase + (pa − paBase)` → 内核侧拷贝读出来。

这条路线**不需要把自己映射进目标进程**——全程在内核侧完成，用户态只拿结果。

### 路线 B：`vm_remap` 共享映射（**不走 ③**，纯用户态）

这是另一条独立的路，而且它**不需要任何内核读写能力**——全是 Mach API。
样本在这条路上"拿目标内存"的关键只有两个参数：**`copy = 0`** 和 **`src_task = 目标进程的 task port`**。

**A. `copy` 参数：**

- `copy = 1` → 映射建立那一刻**复印一份**。复印件**不会跟着原书变**。
- `copy = 0` → 映射**直接指向原页**，之后目标进程写入的内容立刻可见。

曾经的故障形态（**现已修复，留作判据**）：连续 18 次全读到 0。地址算对了、进程挂对了、
映射也建起来了，但那是 `copy = 1` 的复印件——冷启动时建立的，那会儿目标还没初始化，
复印件上是 0；后来目标写了真正的指针，复印件不会跟着变。
**18 次全 0 不是 18 个错误，是 1 个错误被读了 18 遍。**

**B. `src_task` 参数（同样关键，且更容易被忽略）：**

```c
vm_remap(target_task, &target_address, size, mask, flags,
         src_task, src_address, copy, &cur_prot, &max_prot, inheritance);
```

要让窗口看见**目标进程**的内存，`src_task` 必须是**目标进程的 task port**；
若传 `mach_task_self_`，那只是"自己在映射自己"，只能得到自己地址空间里的一个别名。
样本现场是 `x0 = 目标 task`、`x5 = 源 task`（两者同一个值）——**它映射的是目标进程自己的页**。

**样本的完整建窗链**（`sub_100f756c4`，每一步都有二进制证据）：

```
① mach_vm_allocate  flags = 9，大小 = 页数 << 14              @0x100f75738
② 三次 mach_vm_allocate  flags = 0x4002 (OVERWRITE|PURGABLE)  @0x100f75890/758bc/758ec
③ 浇灌 memset 'A' → 'B'                                       @0x100f7592c / 0x100f75ae8
④ vm_remap(copy = FALSE)                                      @0x100f75a34
⑤ mach_vm_protect                                             @0x100f75aa8
⑥ mlock 循环 65534 次 (0xFFFE) + 收尾一次                      @0x100f75af8 / 0x100f75b3c
⑦ pthread_create → 线程 0x100f75d30 再对整个窗口 mlock         @0x100f75b70
   拆窗：mach_vm_deallocate                                    @0x100f75c34
```

**四步扫描序列**（映射 → 锁定 → 拷贝 → 撤销）：

```
1. vm_remap(copy = 0, flags = 0x4000)   建立共享映射（0x4000 = VM_FLAGS_OVERWRITE，
                                        要求地址可预测，避免内核挑到别处）
2. mlock(映射区)                         把页钉在内存里，防调页
                                        （调页开销记在目标进程头上，所以要自己先钉住）
                                        专用线程做，主线程用原子标志 + usleep 轮询
3. vm_copy(源映射 → 本地缓冲)            把共享映射"落定"，之后映射窗口可安全关闭
                                        （COW 语义，登记而非搬运，很快）
4. mach_vm_deallocate(映射)              撤掉书架
```

**四步是为"扫描"优化的**——在一大片内存里找特征码，每块只碰一次就不回来。

高频读取（每帧读坐标）不能照抄：每帧做一次映射+锁定+拷贝+撤销是四次内核往返，
比直接读还慢。高频路径要的是**常驻共享映射**：

```
① vm_remap(copy = 0)                          一次性
② mach_vm_protect(..., set_maximum = 1, VM_PROT_READ)   立刻降权只读
③ 之后每帧本地内存读                            零内核调用
④ 目标退出 / 切后台 / detach 时统一撤销
```

第 ② 步不能省：`copy = 0` 的区域定义上就是 **read-write**，共享映射默认带写权限。
`set_maximum` 必须传 1 —— 只降 current 的话"上限"还留着写权限，
之后一句 `mach_vm_protect` 就能提回来。**降权失败就丢弃这个映射，不要放行。**

## 六、与本工程的对照（差异清单）

### 6.1 本工程当前实际状态（已核实，不是推测）

查过源码，与本报告早期版本的说法不同：**建窗那一段，样本的每一步本工程都已经抄了，
而且逐步骤标了样本的二进制地址**（`MemoryProbe.swift:434-450`）。下面这些**不是缺口**：

| 项 | 状态 |
|---|---|
| `vm_remap` 的 `copy = FALSE` | 已改对（`MemoryProbe.swift:642-643`，第 9 实参 = `0`） |
| `mach_vm_allocate` / 浇灌 / `mach_vm_protect` / `mlock` 循环 / 拆窗 | 已实现，各步注释都指向样本地址 |
| `mach_vm_deallocate` 拆窗 | 已实现 |

**真正的缺口只有一处**，而且是关键的那一处：

```swift
// MemoryProbe.swift:642-643
let rk = remapFn(mach_task_self_, &alias, total, 0, vmFlagsAnywhere,
                 mach_task_self_, base, 0, &curProt, &maxProt, 0)
//                ^^^ target_task        ^^^ src_task —— 两个都是自己
```

**`src_task` 传的是 `mach_task_self_`**，即"自己在映射自己"，得到的只是自己地址空间里的
一个 **alias**（代码注释也明说它"只有一个用途：证明 `copy = FALSE` 语义成立"）。

而样本在对应位置（`@0x100f75a34`）传的是 —— 代码注释自己记着 ——
`x0 = 目标 task`、`x5 = 源 task`（两者同一个值）。
**样本映射的是目标进程自己的页；本工程映射的是自己的页。**

这就是"窗口建起来了、却读不到目标内存"的根因：
不是 `copy` 的问题（那个已经对了），是 **`src_task` 没换成目标进程的 task port**。

### 6.2 一条更容易被忽略的推论

代码注释里另有一处写着：那一步"让窗口的页指向目标物理页（PTE 改写）是整个方案里
**唯一没有样本直接证据**的部分"（`MemoryProbe.swift:435`）。

对照样本实测结论——**样本根本不写 PTE**——这句话的含义就变了：本工程想用
"自建窗口 + 改 PTE 指到目标物理页"达到目标，而样本实测结论是**样本根本没走这条路，
它直接用 `vm_remap(src_task = 目标)` 一步到位**。

所以"改 PTE"这一步很可能**根本不需要**：它是为"`src_task` 只能是自己"这个前提
找的补偿手段。把 `src_task` 换成目标的 task port，这一步的前提就不存在了。

### 6.3 差异总表

| 环节 | 样本 | 本工程 | 结论 |
|---|---|---|---|
| 内核读写能力 | `receivedHandoff` + IOSurface 客户端 | libkfd `kread_sem_open` | 都能用；本工程已通 |
| kernel base | 硬编码锚点 + 扫 `0xFEEDFACF` | XPF 符号 + slide + 自检 | **样本的路绕开了本工程全部难点** |
| slide / 链接基址口径 | 不需要这个概念 | 是核心，偏 133 MB 未归因 | 若改走扫描，这一整类问题消失 |
| 物理读写 | `(vaBase, paBase)` + 内核侧拷贝 | `g_linear_delta` + kread | 公式同型；本工程 delta 闭环死锁 |
| 建窗七步 | 有 | **已按样本实现** | 无缺口 |
| `vm_remap` 的 `copy` | `FALSE` | **已改对** | 无缺口 |
| `vm_remap` 的 `src_task` | **目标进程 task** | **`mach_task_self_`** | **← 唯一实质缺口** |
| 改 PTE 指到目标物理页 | **不做**（不需要） | 列为待做 | 很可能是多余的补偿手段 |
| 物理换算落空判据 | `!((pa < gPhysBase) \|\| ((pa - gPhysBase) >= gPhysSize))` | `km_phystokv` 要求 pa 落在同一区间 | **两边判据一致，可互相印证** |
| 地址校验 | 热路径不校验 | 每步形态门 + 不通过即停 | 本工程更严（因为重启代价） |
| kcall | 不调用 | 不调用 | 一致 |

### 6.4 最值得改的一处

**把 `vm_remap` 的 `src_task` 从 `mach_task_self_` 换成目标进程的 task port。**
这是当前唯一确知的、能直接通向"读到目标内存"的改动，而且：

- 纯 Mach API，**不碰内核读写**，失败最多是 `KERN_*` 返回码，
  **不会整机重启**——风险与收益完全不成比例地划算；
- 换完之后，"自建窗口 + 改 PTE"那一步的必要性可以直接重新评估，很可能整段删掉；
- `mlock` / 降权只读 / 拆窗都已经在位，换掉 `src_task` 之后它们立刻就有意义了。

### 6.5 次值得改的两处

- `flags` 用 `VM_FLAGS_OVERWRITE (0x4000)` 而不是 `VM_FLAGS_ANYWHERE (0x0001)`，
  让地址可预测（样本的做法）。锦上添花，不是关键路径。
- **kernel base 可以改走扫描** —— 见下面 6.7，但**先看清它的边界**。

### 6.7 关于"改走扫描路线"的边界（外部评审已纠正的一处过度表述）

本文早期版本写过"若改走扫描，这一整类问题消失"。**那句话是错的。**
扫描路线省掉的是**"求 slide → 拼 kernel base → 自检"这一段**，不是全部依赖：

| 信息 | 找到运行时 base 后是否自动获得 |
|---|---|
| 运行时映像起点 | 验证映像身份后可以 |
| 链接基址 | **不会**。需要匹配的映像元数据等依据 |
| slide | 仍需"运行时地址 − 链接期地址"这个对应关系才能算出 |
| `ptov_table` / `gVirtBase` / `gPhysBase` / `gPhysSize` 等符号位置 | **不会**。仍要符号解析、特征定位或可靠相对偏移 |

**后三项对本工程是硬需求**——物理换算全靠它们。样本同样依赖：它的 `phystokv`
判据 `!((pa < gPhysBase) || ((pa - gPhysBase) >= gPhysSize))` 就用到那几个符号。
所以扫描路线**不能替掉符号解析**，只能替掉 slide 那一段。

### 6.8 扫描路线在本工程上的两个硬前提（尚未解决）

**前提一：锚点不可信。** `0xFFFFFFE3831F8000`、`+0x28`、16 KB 这三者已经包含了
**地址、结构布局、对齐**三方面的假设。样本里没有版本判断代码，只能说明
**"这里没有显式匹配版本"，不能反证这些假设跨设备 / 跨版本 / 跨重启成立**。
这个地址可能是特定环境的固定映射，也可能是更早阶段准备出来的地址，
甚至只是某次运行记录下来的值。XNU 的地址布局本身就区分不同构建配置，
因此不能仅凭"长得像内核地址"推断其通用性。**在确定来源之前，不要把它当通用入口。**

**前提二（更硬）：`0xFEEDFACF` 命中只能算候选，而且"逐页扫"在本工程的读原语下不安全。**

- 魔数是 **64 位 Mach-O 的通用标记，不是内核专属**。命中的可能是
  **fileset 容器头**，也可能是 **`com.apple.kernel` 本体**。两者基址混用，
  即使魔数正确，后续地址照样算错。样本面对的正是 fileset 结构
  （它自己有 `Fileset Kernelcache UUID` 日志），**所以"命中后是否还有验证步骤"
  必须确认**——本文的分析报告未回答这一点。
- 更关键：`km_read_u32`（`KernelMemory.m:1105`）虽然返回 4 字节，但底层
  **内核实际访问范围更大**（它从改写后的指针起按 `fill_pseminfo()` 逐字段读）。
  现有检查只约束**地址形态与页内边界**，**证明不了那一页已映射**，
  也不能保证访问失败时安全返回。**所以"每页只读 4 字节"并不保证扫描安全。**
  这一点与是否知道 slide 无关。

  `KernelMemory.m:669` 的注释记录过同一教训：反向盲扫被删除，理由正是这个。

**因此**：扫描路线在本工程上不是"更简单的路"，而是**必须先解决"怎么证明一页已映射"
才能用**。而这个难题同时挡着 `proc_ro` 链、`p_list` 遍历、以及这条扫描路线——
它是本项目的核心障碍，不是某一条支路的细节。

样本为什么不在乎？因为它踩错最多返回失败；本工程的 kread 踩错是**整机重启**。
这条差异不改，任何"逐页试"的做法都不能照搬。

### 6.9 扫描路线已经被本工程用两次彩屏否掉过（不是新风险）

这一条是本文成稿后补查到的，它把上面 6.8 的前提二从"理论风险"变成"已有实测代价"：

```
KernelMemory.m:670   反向扫描（唯一一处"在未验证地址上连续盲扫"的内核访问）已经整段删除，
                     g_kernel_base 不再有任何写入点
KernelMemory.m:2271  第二次彩屏的 far = 0xfffffe1564a385b4、DFSC=6 level 2 正是
                     "形态合法、页未映射"这个形态
KernelMemory.m:2276  它与"已经整段删除的那条 kernel base 反向盲扫"同一种赌
```

**样本那条路（锚点 + 向低地址逐页扫 `0xFEEDFACF`）正是本工程已经删掉的那一条。**

所以：`km_read_u32` 只取 4 字节这件事**给不了任何安全性**——底层内核实际访问的范围更大，
而只要目标页没映射，就是 data abort、就是重启，**没有"读到垃圾"这个中间态**。

### 6.10 出路：用页表验证代替盲扫（这条才是可做的）

同一段注释把恢复前提写明了（`KernelMemory.m:2285-2287`）：

> 拿到「**能证明某个地址确实已映射**」的手段 —— `ptov_table` 的等价物
> （对任意 PA 证明它补回后的 KVA 落在映射区内），**或逐级页表验证下钻**。

**"逐级页表验证下钻"是可行的那一条**，而且本工程已经有走页表的代码
（`km_page_table_walk`，`KernelMemory.m:1622`）。要点：

- **只读页表**（`kernel_pmap` 自己必然是已映射的），逐级检查各级表项的 **valid 位**；
- 某一级无效 ⇒ 该 VA 未映射，**直接判否并停止**，不去碰目标地址；
- **全程不产生"读目标地址"这个动作**，所以不构成盲读 —— 这正是它与扫描的本质区别：

  > 扫描会读**目标页**；页表验证只读**已确认映射的页表页**，被查的结果只是一个判定。

这条一旦成立，同一份能力会同时解锁三处：`proc_ro` 链、`p_list` 遍历、以及本工程的
kernel base 定位。**它是本项目的总钥匙，优先级高于任何单条路线。**

### 6.6 不要抄的一件事

**热路径不做校验。** 样本可以这么做，是因为它踩错最多返回失败；本工程的 kread 踩错
是整机重启。这个差异决定了校验强度不能对齐。
