# Aether 内核读取链：三处请复核（供外部模型）

> 用法：整篇直接发给对方。三处问题各自独立，可以只答其中一处。
> 每处都请明确给出「成立 / 不成立 / 证据不足」，并附最小反例或反证；不要用"通常""一般"代替结论。
> 回答请用简体中文，标识符 / 寄存器名 / 位值保留原形。

---

## 背景（最小必要，全部为通用事实）

平台：Darwin 22.4.0 / xnu 8796.102.5 / arm64e / 16 KB 页 / `T1SZ_BOOT = 17`。

读取原语：官方公开项目 libkfd 的 `kread_sem_open` 后端。要读内核地址 `kaddr`，先把自己持有的一个内核对象的**指针字段**改写成 `kaddr - delta`，再调 `syscall(SYS_proc_info, PROC_INFO_CALL_PIDFDINFO, ...)`，由内核按内核语义从该指针开始解引用，把结构体内容拷回用户态。

这条路径上内核没有注册 fault-recovery handler：一旦内核踩到未映射地址，结果不是本进程报错，而是**整机 panic**。因此每次读之前只能做形态检查（地址是否落在内核 VA 域、是否对齐等），而这些检查**都不回答"这个地址已映射吗"**。

## 第一处：一次 panic 的机制重构，以及检查该覆盖哪些访问

panic 记录（16 KB 页）：

```
esr    = 0x96000007        EC = 0b100101 (same-EL data abort), DFSC = 0b000111 (level-3 translation fault)
far    = 0xfffffe1009577ffc
x8     = 0xfffffe1009577ff4        far == x8 + 8
Zone map: 0xfffffe100e4000 - 0xfffffe1610e4000
kernel text base: 0xfffffe0022084000
Panicked task: pid 370
```

已知读取原语的下溢量（`kread_sem_open.h:147`）：

```c
u64 new_pinfo = kaddr - offsetof(struct pseminfo, psem_uid);
```

`struct pseminfo` 布局（`static_info.h:556-567`，16 KB 页）：

```
偏移 0x00  u32  psem_flags
偏移 0x04  u32  psem_usecount
偏移 0x08  u16  psem_mode
偏移 0x0C  u32  psem_uid
偏移 0x14  u64  psem_semobject
偏移 0x1C  u64  psem_label
偏移 0x24  u64  psem_creator_pid
偏移 0x2C  u64  psem_creator_uniqueid
sizeof     = 0x34
```

**Q1.1** 按「调用方传入目标地址 `T`、内核自己算 `P = T - 0x0C` 后按 struct 语义解引用」这个模型，请写出必须从 `T` 的页内偏移上施加的**完整**条件，使这次读取的**每一个**源访问都落在同一页内。请分别给出「内核只读某个子集字段」与「内核按 sizeof 整结构体读取」两种情形的条件。

**Q1.2** 当前检查只做了下界（`T 的页内偏移 >= 0x0C`），没有任何上界。请给出上界的准确值，并指出这个检查在什么地址上会放行一次**跨到下一页**的读取 —— 给一个具体地址作为最小反例。

**Q1.3** 若内核的拷贝实现按 8 字节步进，是否**必然**存在对源区间末尾之外的读取？请区分「实现可以用重叠首尾 load 或单独处理尾部」与「实现必然多读」，并说明：在没有该 copy 实现源码的情况下，哪些结论能下、哪些只能标为证据不足。

**Q1.4** 写方向：写入前内核先用**同一个 `kaddr`** 做一次 8 字节读，写入本身的下溢量是 `0x08`（`kwrite_dup.h:126` 的 `fileproc_guard.fpg_guard`），而那次预读的下溢量是 `0x0C`。当前实现取两者较大者 `0x0C` 作为统一下界。这个取法在什么情况下**不够**？请给出正确形式（按每条路径各自的 delta 与各自的正向访问范围分别约束）。

**Q1.5** 页面大小：调用方用 `getpagesize()` 一类的**用户侧**页大小做页掩码运算，被检查的地址是**内核侧**地址。请说明这两者是否必须相同、在什么条件下会不同、以及按错误粒度做掩码会产生什么样的具体反例地址。

## 第二处：指针高位还原的算术与判据

公开库里的宏（`static_info.h:96-100`）：

```c
ONES(x)       = (1ULL << (x)) - 1
PTR_MASK      = ONES(64 - T1SZ_BOOT)      /* T1SZ_BOOT = 17 → 0x00007fffffffffff */
PAC_MASK      = ~PTR_MASK                 /* 0xffff800000000000 */
SIGN(p)       = ((p) & BIT(55))
UNSIGN_PTR(p) = SIGN(p) ? ((p) | PAC_MASK) : ((p) & ~PAC_MASK)
```

实测：内核里 `task` 结构的 `map` 字段（结构内偏移 `0x28`）读回来是 `0x52bc7e10023e93c0`。

**Q2.1** `UNSIGN_PTR(0x52bc7e10023e93c0)` 等于多少？请一步步算。

**Q2.2** 上面宏的 **false 分支**写的是 `p & ~PAC_MASK`。请写出它化简后的值，指出这样写会把哪一段位清掉，并给出正确的写法。再给一个**输入落在下半地址空间**时的具体反例，使错误分支产生一个非零、且看起来合理但实际错误的地址。

**Q2.3** `SIGN(p)`（单个 bit 55）能不能用来判断"这个指针曾被签名"？请给出一个未签名、canonical、但 `SIGN(p)` 为真的具体地址作为反例；然后说明它**能**正确回答的是哪个问题。

**Q2.4** 「内核 VA 的 bit 55 恒为 1」这个前提在 `T1SZ_BOOT = 17` 时成立吗？请给出理由，并说明 `T1SZ` / `T0SZ` 是否可各自独立配置 —— 如果独立，那对"只操作内核侧地址"的调用方有什么实际影响（会不会产生误判）。

**Q2.5** arm64e 上哪些内核结构字段会被指针认证签名？有没有一条**可判定**的规则（例如"凡是指向 zone 分配对象的 `__ptrauth` 字段"），可以逐字段判断而不必逐设备实测？如果没有，最接近的实用替代是什么、它覆盖不到哪些情况？

## 第三处：从 EL0 建立物理内存访问的两条路线，该怎么选

同一份公开源码（opa334/Dopamine）里有两条物理访问路线，它按"有没有 kcall"二选一（`boomerang.c:86`：`physrwPTE = firstRetrieval && !is_kcall_available();`）：

**路线 A（`physrw_pte.c`）**：把一个页表页映射到自己的地址空间固定 VA（`MAGIC_PT_ADDRESS = L1_BLOCK_SIZE * (L1_BLOCK_COUNT - 1)`，16 KB 设备上是 `0x7000000000`），使该页表页成为普通用户态内存；之后要映射某个物理页 `pa` 就执行 `gMagicPT[i] = pa | PTE_LEAF`（**普通 EL0 store**），再访问 `MAGIC_PT_ADDRESS + i * 16384`。

**路线 B（纯线性换算）**：不碰页表。持有一对基址 `(vaBase, paBase)`，把物理地址换算成内核虚拟地址 `kva = vaBase + (pa - paBase)`，再交给已有的内核拷贝原语读写。

两条路线在我们手上都能用，我需要在动手前把下面几点判清楚。

**Q3.1** 路线 A 里，重写 PTE 之后用户态那次访问要看到新映射，架构上需要哪些同步？请把下面三件事分开说清，并各给结论：
   (a) `dmb sy` —— 它提供什么顺序？它**会不会**导致或蕴含地址翻译失效？请明确回答。
   (b) 改一个软件维护的 ASID 字节值再 `usleep(0)`（让出 CPU）—— 架构上有任何规则要求那次让出必须使旧 ASID 的 TLB 条目失效吗？如果稍后把该字节改回原值，旧条目会不会重新变得可达？
   (c) 上面 Dopamine 的做法是**只在初始化尾部调一次** `flush_tlb()`，而每次映射新物理页**不调**、只 `usleep(0) + dmb sy`。请评估：在什么条件下这够用，在什么条件下不够（尤其是"槽位本来是 0、改成有效"与"槽位已有效、改输出地址"这两种情形的区别）。

**Q3.2** break-before-make：目标项**当前无效**、写入后变有效，需要 BBM 吗？目标项**已有效**、只改输出地址位而描述符类型与属性不变，需要什么、跳过会怎样？请引用 Arm ARM 的条目编号。

**Q3.3** 一个进程在无法自己执行 `tlbi`（EL0 无此权限）的前提下，架构上**成立**的翻译失效手段有哪些？请逐条评估：翻转软件 ASID 字节并让出、只填从未有效过的槽位、每次映射新分配一张页表页、依赖调度器引起的上下文切换、以及每次访问都经过一次会切换上下文的系统调用。如果必须组合，请给出顺序。

**Q3.4** 反过来看路线 B：它完全不需要翻译失效，因为不新建映射。代价是什么？请具体指出：在"目标物理页不在线性映射段"、"目标进程与调用者不属于同一地址空间"、"目标页被压缩 / 换出 / 属于某个保护区"这些情况里，哪些会让路线 B 失效、哪些不会；以及路线 B 对 `(vaBase, paBase)` 这对值的正确性有什么前提（例如：这层线性关系在什么范围内成立、超出范围时会静默算错还是崩溃）。

**Q3.5** 最后：如果两条路线都能建立物理页读写，那么"读另一个进程的某个虚拟地址"这个最终目标上，两条路线各自的**剩余步骤**是什么？请指出哪一条的剩余步骤更少、以及各自的失败模式（是崩溃，还是静默读错）。
